비용 리포트는 왜 청구서를 줄이지 못하는가 — Cloud Custodian

태그 한 줄에 기한을 적어 두는 것만으로 자동화가 성립하는 구조

이런 상황이 있다면 — 매달 비용 리포트를 뽑고, 담당자를 찾아 물어보고, 답이 없어 그냥 두고, 다음 달에 같은 리포트를 또 뽑음.

무엇이 빠져 있는 걸까?

1. 문제 상황

리포트에는 "누가, 언제까지"가 없음

리포트가 답하는 것은 "얼마 썼는가" 하나뿐임.

  • EC2가 20% 늘었다 — 어느 인스턴스인지, 아직 쓰는지는 안 나옴
  • 지출의 40%가 untagged — 누구에게 물어야 하는지 안 나옴
  • ✕ 그래서 아무것도 지워지지 않거나, 급하게 지웠다가 장애가 나서 활동 자체가 중단됨

낭비를 찾는 일은 쉬움. 어려운 것은 자동화해도 안전할 만큼 약하면서, 행동을 바꿀 만큼 강한 조치를 찾는 것.

푸는 방법 중 하나 — 리포트와 삭제 사이에 조치를 하나 더 만듦.

2. 원리

정책은 세 조각이 전부

Custodian은 YAML을 boto3 호출로 바꾸는 규칙 엔진임. 배울 문법은 셋뿐.

resource는 describe API, filters는 남길 것, actions는 남은 것에 할 일

policies:
  - name: ec2-missing-cost-tags
    resource: aws.ec2          # DescribeInstances
    filters:                    # 모두 통과해야 남음(AND)
      - "tag:Owner": absent
    actions: [stop]            # 살아남은 것에만 적용

actions 블록이 없으면 아무것도 못 바꿈. 시작은 항상 조회 전용 정책으로 함.

2. 원리

filter는 describe 응답 위에서 돔

  • API 필터가 아니라 받아 온 JSON을 프로세스 안에서 거름
    • 그래서 State.Name처럼 중첩 필드도 그대로 주소로 씀
  • filters는 기본 AND. or, not 블록으로 묶을 수 있음
  • 리소스 종류가 달라도 문법은 그대로임 — aws.ec2든 aws.rds든 tag:Owner 표기가 같음
  • 지표가 필요한 필터(type: metrics)만 CloudWatch를 추가로 호출함

describe 응답만 보는 필터는 값이 싸고 정확함. 밖에 물어보는 필터는 틀릴 수 있음 — 이 차이가 뒤에서 조치 수위를 가름.

2. 원리

태그가 곧 상태 저장소

리포트와 삭제 사이에 있는 조치가 mark-for-op. 하는 일은 태그 하나 쓰는 것뿐임.

정책이 쓰는 값과, 리소스에 실제로 박히는 태그

actions: [{type: mark-for-op, tag: c7n_tag_compliance, op: stop, days: 4}]

# 리소스에 남는 것
c7n_tag_compliance = "Resource does not meet policy: stop@2026/08/01"

짝이 되는 filter marked-for-op이 이 태그를 되읽어, 날짜가 지난 것만 고름.

2. 원리

상태를 리소스가 들고 있어서 생기는 것

  • 엔진이 DB도 state 파일도 안 가짐 → 노트북에서 돌리든 Lambda에서 돌리든 같은 결과
  • 기한이 콘솔에 그대로 보임 → 담당자에게 리포트를 보낼 필요가 없음
  • 태그를 고치면 세 번째 정책이 mark를 지움 → 수정이 곧 취소, 티켓 불필요

그래서 규칙 하나는 보통 정책 세 개로 씀.

① mark기한 기록
→
② unmark고쳐지면 취소
→
③ act기한 지나면 stop

policies/2-tag-enforce.yml이 정확히 이 모양임

4. 실행 모드

같은 파일이 세 곳에서 돔

배포 위치는 운영 결정이지 정책 재작성이 아님. 파일은 그대로 둠.

  • pull — 내 쉘이나 CI에서 custodian run. 규칙을 쓰고 시험할 때
  • periodic — EventBridge 스케줄로 도는 Lambda. 태그 강제와 offhours
  • cloudtrail — API 이벤트에 반응하는 Lambda. 생성 순간에 잡을 때

상태를 리소스가 들고 있으므로 모드를 바꿔도 진행 중인 유예 기간이 그대로 이어짐. pull에서 --dryrun으로 시작해, 숫자가 더 놀랍지 않을 때 periodic으로 옮김.

5. FinOps 레버

줄일 수 있는 것은 네 종류뿐

describe만 보면 되는 것

  • 주인 없는 지출 — tag:Owner absent
  • 업무 시간 외 유휴 — type: offhour
  • 고아 리소스 — State: available

바깥에 물어봐야 하는 것

  • 과대 사양 — type: metrics(CloudWatch)

앞의 셋은 사실 확인이라 틀릴 수 없음. 마지막 하나만 추정이고, 그래서 조치 수위가 다름.

5. FinOps 레버

레버 ① 태그 거버넌스

같은 파일 안의 세 정책. 나머지 레버의 예외 처리도 전부 태그로 이뤄짐

# ① 기한 기록. 오늘은 아무것도 안 멈춤
filters: ["tag:Owner": absent]
actions: [{type: mark-for-op, op: stop, days: 4}]
# ② 고쳐졌으면 기한 취소
filters: ["tag:Owner": not-null]
actions: [{type: remove-tag, tags: [c7n_tag_compliance]}]
# ③ 기한이 지난 것만. terminate가 아니라 stop
filters: [{type: marked-for-op, op: stop}]
actions: [stop]

체크포인트. ③이 stop인 이유 — 되돌릴 수 있는 조치라야 자동화해도 됨.

5. FinOps 레버

레버 ② 업무 시간 외 정지

주 168시간 중 개발 환경이 실제로 쓰이는 시간은 40시간 남짓. 즉효가 가장 큼.

opt-out은 "태그로 빼지 않으면 전부 대상"이라는 뜻

filters: [{type: offhour, tag: c7n_schedule, default_tz: Asia/Seoul,
            offhour: 20, opt-out: true}]
  • opt-out true면 기본이 정지, c7n_schedule=off인 것만 예외
  • opt-in이면 태그 붙인 것만 정지 — 안전하지만 아무도 안 붙여서 절감이 0이 됨
  • ✕ RDS는 7일 뒤 AWS가 자동으로 다시 켬 — start 정책은 선택이 아님

이 정책의 성패는 opt-in/opt-out 한 줄에서 갈림. 절감과 항의가 여기서 결정됨.

5. FinOps 레버

레버 ③ 주인이 이미 떠난 리소스

  • 미사용 EBS — State: available. 붙어 있는 볼륨과 요금이 같음
  • 미할당 EIP — AssociationId: absent. 안 쓰기 때문에 과금됨
  • 오래된 수동 RDS 스냅샷 — 자동 스냅샷과 달리 스스로 만료되지 않음

actions는 적힌 순서대로 실행됨. 이 순서가 복구 가능 여부를 가름

actions:
  - type: snapshot   # 먼저
  - type: delete

단, 스냅샷도 돈임. 지우려고 만든 정책이 몇 달 뒤 그 비용을 그대로 되살릴 수 있음. 스냅샷 만료 정책과 짝으로 둠.

5. FinOps 레버

레버 ④ 과대 사양 — 유일하게 틀릴 수 있는 것

14일 평균 CPU 5% 미만. 그런데 조치는 태그까지만

filters: [{type: metrics, name: CPUUtilization,
           days: 14, value: 5, op: less-than}]
actions: [{type: tag}]   # stop도 resize도 아님
  • CPU가 낮다는 사실은 정상적인 대기 상태와 구별되지 않음
  • 그래서 사람이 판단할 목록을 만들어 주는 데까지만 함
  • terminate가 필요하면 mark-for-op에 14일 정도의 긴 기한을 걸어 사람이 개입할 시간을 둠

6. 실습

계정 없이 파이프라인을 관찰

mock AWS(moto)에 EC2 2대, 미사용 EBS 1개, RDS 1대를 심고 정책을 돌린 실제 출력.

조회 전용 정책 → 태그 강제 정책. 아직 아무것도 멈추지 않음

# 1) actions 없는 정책
policy:ec2-missing-cost-tags count:1   # 2대 중 1대만 걸림
policy:rds-missing-cost-tags count:1

# 2) mark 정책. stop 정책은 같은 실행에서 0건
custodian.actions:INFO Tagging 1 resources for stop on 2026/08/01
policy:ec2-untagged-stop count:0

체크포인트. 두 인스턴스의 차이는 Owner 태그 하나뿐. 정책은 그 차이만 보고 갈랐음.

7. 반전

두 번째 실행이 아무 일도 안 함

태그 날짜를 과거로 바꾸고 같은 파일을 다시 돌렸는데 stop이 0건으로 나옴.

policy:ec2-untagged-mark  count:1   # 이미 마크된 리소스인데 또 걸림
policy:ec2-untagged-stop  count:0   # 기한이 지났는데 안 걸림
  • 범인은 describe 결과 로컬 캐시 — 기본 15분. 방금 쓴 태그가 안 보임
  • 단서는 두 정책이 동시에 어긋난 것. 필터가 틀렸다면 한쪽만 어긋남
  • 해결 — custodian run --cache-period 0

같은 실행에서 mark와 act를 붙여 두면 캐시 때문에 하루치 동작이 통째로 밀릴 수 있음. 운영에서 둘을 분리해 배포하는 이유이기도 함.

8. 안전장치

비용을 줄이는 정책과 사고를 내는 정책은 같은 정책

  • --dryrun으로 먼저 개수를 봄. 예상보다 많으면 필터에 계정·태그 범위를 더함
  • mark 정책을 먼저 일주일 배포하고 act는 나중에 — 필터가 틀렸음을 싸게 아는 유일한 방법
  • out/의 resources.json을 보관. 사고 뒤에 엔진이 무엇을 봤는지에 대한 유일한 증거임

YAML 리뷰가 놓쳤을 때의 마지막 방어선 — 이미 마크된 리소스만 삭제 허용

Action: ["ec2:DeleteVolume"]
Condition: {StringLike: {"aws:ResourceTag/c7n_orphan": "*"}}

필터를 잘못 써도 mark 단계를 거치지 않은 리소스는 삭제 자체가 거부됨.

9. 트레이드오프

얻는 것과 넘겨받는 것

얻는 것

  • 월 1회 수작업 루프가 사라짐
  • 유예 기간이 콘솔에 보여 통보가 필요 없음
  • 엔진이 무상태라 배포 위치를 자유롭게 바꿈

잃는 것

  • 태그가 곧 상태라, 태그를 지우면 유예 기간도 사라짐
  • 정책 하나를 고치면 계정 전체에 즉시 적용됨
  • 절감의 근거가 YAML로 흩어져 리뷰 대상이 늘어남

어디를 봐야 하나. "이 정책이 얼마를 줄이나"가 아니라 "이 정책이 틀렸을 때 무엇이 멈추나".

10. 확인해 보기

스스로 점검 ①

Q1. 태그 날짜를 과거로 바꾸고 정책을 다시 돌렸는데 mark는 또 걸리고 stop은 0건이다. 먼저 의심할 것은?

  • marked-for-op 필터의 op 값이 정책과 다름
  • describe 결과가 로컬 캐시에서 나옴
  • 태그 문자열 형식이 custodian 규약과 다름

두 정책이 동시에 어긋난 것이 단서. 필터나 태그 형식이 문제라면 한쪽만 어긋남. 두 정책 모두 "태그가 없던 시점"의 데이터를 본 것이므로 원인은 입력 데이터, 즉 캐시. --cache-period 0으로 확인.

10. 확인해 보기

스스로 점검 ②

Q2. RDS offhours 정책을 배포했다. 첫 주는 비용이 줄었는데 둘째 주부터 절감이 사라졌다. 가장 그럴듯한 원인은?

  • 인스턴스에 c7n_schedule 태그가 붙어 예외 처리됨
  • AWS가 정지 7일 뒤 인스턴스를 자동으로 다시 켬
  • Performance Insights 때문에 정지가 무시됨

RDS 정지는 최대 7일이고 그 뒤 AWS가 자동 기동함. 이후로는 정지 정책이 매일 다시 멈추지 않는 한 계속 켜져 있음. onhour/offhour를 짝으로 두고, 실제로 실행됐는지까지 확인해야 함.

11. 결론

도입 질문으로 돌아가서

리포트에 빠져 있던 것은 데이터가 아니라 기한이었음. Custodian이 한 일은 그 기한을 리소스 자신의 태그에 적어 둔 것뿐이고, 그것만으로 엔진은 무상태가 되고, 담당자는 콘솔에서 기한을 보고, 태그를 고치면 기한이 사라짐. 사람이 매달 돌리던 루프가 통째로 없어진 이유가 이것임.

기억할 원리 — 상태를 엔진이 아니라 대상에 둔다. 다음에 비슷한 자동화를 만들 때 "이 상태를 어디에 저장할까"가 아니라 "대상 자신에게 적을 수 있는가"부터 물으면 됨.
