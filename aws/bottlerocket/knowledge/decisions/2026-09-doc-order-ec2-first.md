# 문서 순서는 EC2 단독을 EKS보다 앞에 두고, 실습 문서는 원리·실습·트러블슈팅·정리 구조로 쓴다

## 결정

- 읽는 순서는 시나리오 → 원리 → EC2 단독(환경, 첫 접속, 못 하는 것, 설정과 업데이트) → EKS(환경, NotReady 긴급 접속) → 운영이다
- 실습 문서(3~8장)는 원리, 실습, 트러블슈팅, 정리 4개 절을 이 순서로 둔다
- EKS 긴급 접속은 평시 접속이 아니라 `systemctl stop kubelet`으로 NotReady를 재현한 뒤 3가지 경로를 비교하는 시나리오로 쓴다
- 1장에 용어 표와 준비물을 두고, setup 문서는 준비물을 1장으로 링크만 한다

## 이유

- 처음 구성은 원리 → EKS 환경 → 긴급 접속 → EC2 환경 → EC2 실습 순서였다. 입문자가 첫 실습에서 15분짜리 클러스터를 띄우고, Bottlerocket 셸을 한 번도 열어 보기 전에 "긴급 접속"을 만났다
- EC2 단독은 2분에 뜨고 시간당 비용이 EKS의 3분의 1이다. 같은 `aws-k8s-1.36` 변형이라 host container, 설정, 업데이트는 EC2에서 본 결과가 EKS 노드에 그대로 적용된다
- EKS 실습에서 멈추는 원인은 대부분 클러스터 쪽(조인, access entry, CNI)이다. Bottlerocket을 먼저 익혀 두면 8장에서 원인을 분리할 수 있다
- 긴급 접속 문서가 평시 노드에서 3가지 경로를 모두 성공시키면 경로 간 차이가 드러나지 않는다. kubelet을 멈춰야 경로 3만 실패하는 이유가 보인다
- 트러블슈팅을 별도 문서로 모으면 멈춘 자리에서 찾아가야 한다. 실습 문서마다 그 단계의 증상만 두는 편이 입문자에게 맞다
