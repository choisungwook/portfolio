컨테이너 운영, ECS에게 맡기기

docker run 수동 운영에서 출발해 ECS의 동작원리·구조·배포전략을 핸즈온으로 확인하는 학습지

이런 상황이 있다면 — EC2 한 대에서 docker run으로 서비스 운영 중. 새벽에 컨테이너가 죽으면 SSH로 들어가 다시 올리고, 새 버전 배포 때마다 서비스가 잠시 끊김.

어떻게 풀까?

1. 문제 상황

컨테이너 하나를 사람이 지키는 운영

이런 상황을 가정함

EC2 한 대에 docker run으로 웹 서비스 운영 중.

  • ✕ 컨테이너가 죽어도 아무도 모름 — 장애 제보 후에야 SSH 접속, 수동 재기동
  • ✕ 배포는 stop → run 순서 — 그 사이 서비스 중단
  • ✕ 스케일아웃은 EC2 추가·컨테이너 배치·LB 연결 전부 수동

재기동 스크립트로 버틸 수는 있으나, "죽음 감지 → 재기동 → LB 연결"을 직접 만들면 orchestrator 재발명.

푸는 방법 중 하나 — 원하는 상태(컨테이너 수·버전)만 선언하고 유지 책임을 넘기는 container orchestration. 그중 AWS 관리형인 ECS(Elastic Container Service).

2. 원리

선언하면, 시스템이 맞춘다

ECS의 핵심은 desired state 선언. "컨테이너 2개 항상 실행"을 선언하면 service scheduler가 실제 상태(actual)와 계속 비교, 다르면 조정함.

  • 작은 예 — desired count = 2 선언
    • task 1개 죽음 → actual 1 ≠ desired 2 → scheduler가 새 task 1개 기동
  • 설계 이유 — 분산 환경에서 죽음은 일상. 복구를 사람의 절차가 아니라 제어 루프에 맡김
  • (잠깐 용어) task definition = 실행 설계도 / task = 실행 단위 / service = 유지 선언 — 다시 돌아와서, 셋을 잇는 것이 scheduler

다른 곳에도 적용됨. Kubernetes ReplicaSet, EC2 Auto Scaling Group도 같은 reconciliation 원리.

2. 원리

task는 어디서 도는가 — launch type

무엇을 몇 개 띄울지(선언)와 어디서 띄울지(실행 기반)는 분리된 선택 — 실행 기반이 launch type.

  • EC2 launch type — 내가 등록한 EC2 위에서 실행
    • OS 패치·용량 계획이 내 몫. GPU·특수 인스턴스 필요 시 선택
  • Fargate — 호스트 없이 task 단위로 CPU·메모리를 빌림. 서버 관리 제로, task별 과금

Fargate의 등장 이유 — orchestrator가 컨테이너를 살려도 호스트 관리 문제는 남기 때문. 이 학습지 핸즈온은 Fargate 사용.

3. 구조 이해하기

task definition → service → task

설계도(task definition)를 service가 참조해, cluster 안에서 task를 desired count만큼 유지.

task definition이미지·CPU·메모리·포트
→
ECS cluster (Fargate)
servicedesired count = 2
→
task 1
task 2
  • cluster — task·service를 담는 논리 경계
  • service — desired count 유지 + LB 연결·배포 담당
  • task — 실행 중인 컨테이너 묶음

3. 구조 이해하기

task가 죽으면 벌어지는 일

같은 구조 위에서 원리 장의 reconciliation이 도는 장면. 단계를 넘겨 확인.

1
servicedesired = 2
→
task 1
task 2 ✕

1단계. task 2가 비정상 종료. actual count = 1.

2
servicedesired 2 ≠ actual 1
→
task 1
task 2 ✕

2단계. service scheduler가 desired와 actual의 차이를 감지.

3
servicedesired = 2
→
task 1
task 3 (신규)

3단계. 새 task를 기동해 desired 회복. 사람 개입 없음.

4. 핸즈온

① 올릴 이미지를 로컬에서 먼저 확인

ECS task로 띄울 것과 같은 이미지를 로컬에서 실행. 도구 설치는 docs/setup.md 참조.

workspace 루트(aws/ecs/quickstart)에서 실행 — 주석이 기대 결과

docker compose up -d
curl -s http://localhost:8080 | grep title
# 기대: <title>Welcome to nginx!</title>

체크포인트. ECS에 올릴 이미지가 로컬에서 동작함을 확인.

4. 핸즈온

② terraform으로 기반 리소스 생성

service 직전까지를 준비 — cluster, task definition(nginx·ARM64), IAM role, log group, security group(내 IP만 80 허용). service 생성·배포는 console에서 직접.

terraform 디렉터리에서 실행

terraform -chdir=terraform init
terraform -chdir=terraform apply

기대 결과 (마지막 줄)

Apply complete! Resources: 8 added, 0 changed, 0 destroyed.

체크포인트. service를 만들 준비(cluster·설계도·네트워크) 완료.

4. 핸즈온

③ console 입력값을 outputs로 확인

다음 장 console 화면에 그대로 입력할 값들.

outputs 조회

terraform -chdir=terraform output

기대 결과

cluster_name = "ecs-fundamentals"
security_group_id = "sg-..."
subnet_ids = [ "subnet-...", ... ]
task_definition_family = "ecs-fundamentals-web"

체크포인트. cluster·설계도·네트워크 값 확보 — console에서 조립만 남음.

4. 핸즈온

④ console에서 첫 service 생성 (quickstart)

  • 1 ECS console → Clusters → ecs-fundamentals → Services → Create
  • 2 Fargate / Family: ecs-fundamentals-web / Service name: web / Desired tasks: 1
  • 3 Networking — outputs의 subnet·security group 선택, Public IP 켜기
  • 4 Tasks 탭에서 RUNNING 확인 후 task의 Public IP 복사

task public IP로 접속 확인 — 주석이 기대 결과

curl http://<task public IP>
# 기대: <h1>Welcome to nginx!</h1>

체크포인트. 선언(desired 1)만으로 컨테이너가 배치·기동됨.

4. 핸즈온

⑤ task를 죽여서 자동 복구 관찰

도입 문제의 "새벽 SSH 재기동"이 사라지는지 확인 — reconciliation의 실물.

  • 1 Tasks 탭 → 실행 중 task 선택 → Stop
  • 2 수십 초 내 새 task 자동 기동 (PROVISIONING → RUNNING)
  • 3 service → Events 탭에서 복구 기록 확인

Events 탭 기대 메시지

service web has started 1 tasks ... has reached a steady state.

체크포인트. 감지 → 신규 기동까지 사람 개입 없음.

5. 배포전략

배포 = revision 교체, 기본은 rolling

ECS의 배포 = task definition의 새 revision 등록 + service의 참조 교체. 설계도가 불변(immutable)이라 revision 번호로 버전 추적됨.

  • 1 Task definitions → ecs-fundamentals-web → Create new revision — 환경변수 추가(예: DEPLOY_VER=2)
  • 2 service web → Update service → 새 revision 선택
  • 3 Deployments 탭에서 교체 과정 관찰

Deployments 탭 기대 흐름

신 revision task 기동 → 정상 확인 → 구 revision task 종료 (잠시 공존)

체크포인트. 중단 없는 rolling update 관찰 완료.

5. 배포전략

rolling만 있는 게 아니다

  • rolling (기본) — 새 task를 띄우며 구 task를 점진 교체
    • minimumHealthyPercent(유지 최소)·maximumPercent(순간 최대)로 속도 제어
    • 추가 비용 없음. 두 버전이 동시에 트래픽 받는 구간 존재
  • blue/green (CodeDeploy 연동) — 신버전 세트를 따로 띄워 트래픽 일괄 전환. 즉시 롤백, 배포 중 인프라 2배
  • external — 배포 제어를 외부 시스템에 위임

판단 기준 — 두 버전 공존 가능하면 rolling, DB 스키마 비호환 등 공존 불가면 blue/green.

6. 확인해 보기

스스로 점검 (1/2)

Q1. desired count 3인 service에서 task 2개가 동시에 죽었다. 운영자가 할 일은?

  • 새 task 2개를 수동으로 run task 실행
  • 없음 — scheduler가 자동으로 2개 기동
  • service를 삭제하고 다시 생성

scheduler가 desired(3) ≠ actual(1)을 감지해 스스로 채움. 복구는 제어 루프의 일.

6. 확인해 보기

스스로 점검 (2/2)

Q2. desired 2, minimumHealthyPercent 100%, maximumPercent 200%인 service의 rolling 배포 동작은?

  • 구 task 2개를 먼저 내리고 새 task 2개 기동
  • 구 task 1개를 내리고 새 task 1개를 올리는 교대 반복
  • 새 task 2개를 먼저 띄워 정상 확인 후 구 task 2개 종료

minimum 100% → 기존을 먼저 못 내림. maximum 200% → 순간 4개 허용, 새것을 먼저 띄우는 방식만 가능.

7. 트레이드오프

무엇을 얻고, 무엇을 할 수 없는가

얻는 것

  • 제어 평면 무료 — cluster 비용 없음, task 비용만
  • ALB·IAM·CloudWatch 통합이 기본값
  • K8s 대비 낮은 학습 곡선·운영 부담

할 수 없는 것

  • AWS 밖 이식 불가 — 멀티클라우드와 충돌
  • Helm·Operator·CRD 등 K8s 생태계 부재
  • 스케줄러 확장·커스텀 컨트롤러 불가
  • Fargate — GPU 미지원, privileged 불가

언제 쓰는가. AWS 단일 + 표준 웹·배치 워크로드면 ECS 충분. K8s 생태계·멀티클라우드 요구면 EKS 검토.

8. 결론

도입 문제로 돌아가서

  • 죽으면 사람이 재기동 → reconciliation이 자동 복구 (핸즈온 ⑤)
  • 배포 중 서비스 중단 → rolling이 새 task 확인 후 구 task 종료
  • 수동 스케일아웃 → desired count 변경, auto scaling 연동 가능

기억할 한 문장 — ECS는 desired state를 선언하면 scheduler가 actual을 맞추는 시스템. 이 구조는 K8s 학습 시에도 그대로 대응됨.

실습 정리 — console에서 service 삭제 후 terraform destroy (docs/3-cleanup.md).
