이벤트 전 스펙 점검 — 어디까지 버티는가

ALB · Auto Scaling group · Spring Boot · Redis · RDS를 앞에 두고, 무엇을 올릴지 숫자로 답하는 법

이런 상황이 있다면 — 다음 주 화요일 20시 이벤트. "지금 스펙으로 되나요?"라는 질문에 CPU 40%니까 여유 있습니다라고 답함.

그 답이 왜 위험할까?

1. 문제 상황

여유가 있었는데 이벤트가 무너짐

지난 이벤트에서 관측된 순서. 어느 계층도 CPU 100%가 아니었음.

  • 20:00 트래픽 진입. EC2 CPU 45%, 그런데 p99 응답이 200ms → 3초
  • ✕ ASG가 CPU 기준으로 스케일 아웃. 인스턴스 4대 → 12대
  • ✕ 늘어난 순간 RDS 커넥션 상한에 닿고 502·504가 시작됨
  • ✕ 배포로 캐시가 비어 있어 miss가 그대로 DB로 흘러감

스펙이 부족했던 게 아니라, 어디가 한계인지 모른 채로 늘렸음. 늘린 방향이 병목과 반대였음.

푸는 방법 중 하나 — 계층마다 한계를 측정하고, 병목이 공유 자원인지 아닌지로 up/out을 고름.

2. 원리

사용률은 용량이 아님

CPU 40%는 "60% 더 받을 수 있다"는 뜻이 아님. 요청이 스레드가 아니라 커넥션 10개를 기다리는 중이면 CPU는 계속 한가함.

  • 용량의 정의는 하나뿐 — SLO를 깨지 않고 처리하는 최대 요청률
  • 구하는 방법도 하나뿐 — 동시성을 계단으로 올리며 처리량과 지연을 같이 봄
  • 처리량이 평평해지고 지연만 올라가는 지점이 knee. 그 지점이 용량임
  • SRE의 golden signal 중 스케일 트리거로 쓸 것은 saturation 계열 — 큐 길이, 대기 중인 커넥션, 인스턴스당 요청 수

CPU는 결과 지표라 늦게 움직임. RequestCountPerTarget처럼 부하 그 자체에 가까운 값이 트리거로 낫다.

2. 원리

스레드 수와 pool 크기는 계산으로 나옴

Little's Law — 동시 처리 수 = 처리량 × 응답시간. 사이징을 감이 아니라 산수로 바꿔 줌.

목표 500 rps, 응답 40ms, DB 구간 10ms, 인스턴스 4대일 때

# 시스템 전체 동시 요청 수
500 × 0.04s = 20

# DB를 동시에 붙잡는 수 → 인스턴스당 커넥션 pool
500 × 0.01s = 5  →  5 / 4대 = 1.25  # 여유 붙여 4

# 필요한 인스턴스 수 = 목표 rps / 측정된 인스턴스당 rps
500 / 180 = 2.8  →  3대

여기서 인스턴스당 180 rps는 측정값이어야 함. 이 값만 실측이고 나머지는 산수임.

2. 원리

scale up과 scale out을 가르는 한 문장

병목이 인스턴스마다 따로 있으면 out, 모두가 공유하면 up.

scale out이 듣는 경우

  • stateless한 앱 스레드·CPU가 한계
  • 인스턴스가 자기 몫의 자원을 들고 옴
  • 아래 계층에 아직 여유가 있음

scale out이 해로운 경우

  • RDS writer 하나가 한계
  • Redis 샤드 하나(단일 스레드)가 한계
  • 커넥션만 N배로 늘어 상한을 침

공유 병목 앞에서의 scale out은 큐를 옮길 뿐임. 대기 위치가 앱에서 DB로 이동하고, 커넥션 수는 인스턴스 수만큼 곱해짐.

2. 원리

피크만큼 준비하면 피크를 못 넘김

  • 예측은 틀림 — 예상 피크에 오차 계수를 곱함(예: 1.5)
  • AZ 하나가 빠짐 — 3 AZ면 남는 건 2/3. 그 상태로 피크를 받아야 함
  • SRE book의 N+2 — 피크를 받는 용량 + 계획 정비 1 + 예기치 못한 장애 1

목표 500 rps를 계획 용량으로 바꾸는 식

500 × 1.5 # 예측 오차
      ÷ 0.67 # AZ 1개 손실 후 남는 비율
      = 1120 rps # 이 값으로 인스턴스 수를 계산

여유를 얼마나 둘지는 error budget으로 정함. 이벤트에서 얼마를 태워도 되는지가 정해지면 안전계수도 정해짐.

체크포인트. 스펙 점검 산출물에는 "한계를 넘으면 어떻게 되는가"가 반드시 들어감. 정하지 않으면 이벤트 중에 발견하게 됨.

5. 계층별 점검

ALB — 스스로 늘지만 즉시는 아님

메트릭읽는 법
RequestCountPerTarget인스턴스당 부하. 스케일 트리거로 가장 정확함
TargetResponseTime엣지에서 본 지연. 앱 관점과 차이가 나면 큐가 있다는 뜻
HTTPCode_ELB_5XX / 504타깃이 제때 답하지 못했다는 ALB의 판정
RejectedConnectionCount연결 상한에 닿음
  • 계단형 스파이크는 사전 램프 트래픽이나 AWS 지원 요청으로 준비함
  • 타깃의 keep-alive timeout > ALB idle timeout — 반대면 자기가 만든 502가 나옴
  • health check를 너무 민감하게 두면 피크에 느려진 인스턴스가 빠져 용량이 더 줄어듦

5. 계층별 점검

ASG와 Spring Boot — 예측 가능한 이벤트에는 예약이 먼저

  • 시각을 아는 이벤트는 scheduled scaling이 1순위, target tracking은 예측이 틀린 몫을 받는 안전망
  • target tracking 기준은 ALBRequestCountPerTarget, 목표값은 측정한 knee에서 가져옴
  • instance warmup을 준비 시간보다 짧게 두면 과잉 스케일이 일어남
  • 종료 시 graceful shutdown + deregistration delay > 가장 느린 요청

애플리케이션에서 이벤트 때 실제로 터지는 자리

server.tomcat.threads.max=200   # 큐를 감추기만 하고 지연을 늘릴 수 있음
spring.datasource.hikari.maximum-pool-size=10   # 기본값 그대로면 계산을 안 한 것
spring.datasource.hikari.connection-timeout=200   # 무한 대기 대신 빠른 거절

그 외 — 모든 외부 호출의 timeout, jitter 있는 재시도와 재시도 예산, circuit breaker와 bulkhead, 캐시 스탬피드 방지.

5. 계층별 점검

Redis — 샤드 하나의 한계는 코어 하나임

명령 처리는 샤드당 단일 스레드. 노드를 키워도 그 스레드는 하나임. 그래서 CPUUtilization이 아니라 EngineCPUUtilization을 봄.

메모리 임계, eviction 증가노드 타입 up, maxmemory-policy와 TTL 점검
CurrConnections 급증클라이언트 pool 확인. 요청마다 연결은 버그

slow log에 KEYS 같은 O(N) 명령이 있으면 피크에 그 샤드의 다른 클라이언트가 전부 멈춤.

6. Warm pool

준비 시간이 램프보다 길면 정책으로 못 따라감

Warm pool은 미리 부팅해 두고 ALB에는 등록하지 않은 EC2의 집합. 스케일 아웃 때 새로 만들지 않고 여기서 꺼내 씀.

실습 6에서 측정한 준비 시간. EC2에서는 여기에 인스턴스 기동과 user data, JIT·캐시 워밍이 더 붙음

6. Warm pool

쓰기 전에 먼저 없앨 이유를 찾음

warm pool이 맞는 경우

  • 램프가 예측 불가하고 반복됨
  • 준비 시간이 길고 줄일 수 없음
  • scale in 때 pool로 되돌려 재사용

먼저 시도할 것

  • 시각을 아는 이벤트면 예약 스케일링
  • user data 작업을 AMI로 굽기
  • 기동 시 느린 의존성 대기 제거

lifecycle hook은 pool 진입과 진출에 두 번 걸림. 느린 작업은 앞에, 워밍은 뒤에 둠

warm_pool {
  pool_state = "Stopped"
  min_size   = 4
  instance_reuse_policy { reuse_on_scale_in = true }
}

고칠 수 없는 것. 병목이 RDS나 Redis 샤드면 warm 인스턴스는 더 빨리 도착해서 같은 자리에 줄을 설 뿐임.

7. 확인해 보기

스스로 점검 ①

Q1. EC2 CPU 45%, p99는 계속 오르고, ASG가 인스턴스를 2배로 늘렸는데 처리량이 그대로다. 가장 먼저 의심할 것은?

  • 인스턴스 타입이 작아서 CPU 스티어링이 안 됨
  • 모든 인스턴스가 공유하는 하위 계층이 이미 포화됨
  • ALB가 아직 스케일되지 않아 앞단에서 막힘

인스턴스를 2배로 늘렸는데 처리량이 그대로라는 것은 병목이 앱 계층 밖에 있다는 뜻. 실습 2가 정확히 이 상황이며, 이때 늘어난 것은 처리량이 아니라 하위 계층에 꽂힌 커넥션 수다.

7. 확인해 보기

스스로 점검 ②

Q2. 목표 800 rps, 응답 50ms, DB 구간 12ms, 인스턴스 8대다. 인스턴스당 pool 크기로 타당한 출발점은?

  • 40 — 목표 rps를 인스턴스 수로 나눈 값
  • 2 안팎 — 800 × 0.012 ÷ 8 = 1.2에 여유를 더한 값
  • 10 — 기본값이 대부분의 경우에 맞음

pool은 DB를 동시에 붙잡는 수를 인스턴스 수로 나눈 값이다. 크게 잡으면 DB의 max_connections를 인스턴스 수만큼 곱해서 위협하고, 앱은 거절 대신 DB를 대기시킨다.

8. 결론

도입 질문으로 돌아가서

"CPU 40%니까 여유 있다"가 위험한 이유는, 사용률이 용량이 아니기 때문임. 용량은 SLO를 깨지 않는 최대 요청률이고 계단 부하로 측정해야 나옴. 그 숫자가 나오면 나머지는 산수임 — Little's Law로 스레드와 pool을 계산하고, 오차와 AZ 손실로 여유를 붙임.

기억할 원리 — 병목이 공유 자원이면 늘리는 방향은 위가 유일함. 그리고 한계를 넘은 뒤의 동작(거절할지 대기시킬지)을 이벤트 전에 정해 두는 것까지가 스펙 점검임.
