이벤트 D-7, 무엇을 점검할 것인가 — 스케일 판단과 warm pool

EC2(ASG) + internet-facing ALB + Redis + RDS 위 Spring Boot API의 사전 용량 점검

이런 상황이 있다면 — 다음 주 대형 이벤트로 트래픽 10배 예상. "인스턴스와 DB 스펙을 미리 점검하라"는 지시를 받음.

무엇을, 어떤 기준으로 점검할까?

1. 문제 상황

"여유 있어 보임"은 점검이 아님

흔한 점검의 모습을 가정함.

  • ✕ 대시보드를 훑고 "CPU 30%라 여유 있음"이라고 보고 — 평시 수치일 뿐
  • ✕ 일단 인스턴스를 2배로 늘려 둠 — 병목이 DB면 돈만 쓰고 그대로 죽음
  • ✕ auto scaling이 있으니 알아서 될 것 — 스파이크는 초 단위, 스케일 아웃은 분 단위

필요한 것은 네 가지 — ① 수치화된 예상 부하 ② 계층별 포화 지점 실측 ③ 병목 유형별 up/out 판단 규칙 ④ scale out의 시간 벽 대응.

푸는 방법 중 하나 — SRE 관점에서 각 계층의 saturation(포화까지 남은 거리)을 재고, 병목의 정체로 up/out을 정함.

2. 원리

점검의 축은 saturation

Google SRE book의 4 golden signals. 무엇을 볼지 모를 때 돌아오는 기준점.

  • latency — 응답이 얼마나 걸리는가. 성공과 실패의 latency는 따로 봄
  • traffic — 시스템에 얼마나 요청이 오는가 (RPS)
  • errors — 실패율. 명시적 5xx와 "200이지만 느려서 사실상 실패"를 포함
  • saturation — 가장 제약된 자원이 한계까지 얼마나 남았는가

사전 점검이 묻는 것은 넷 중 saturation임. 평시 대시보드가 아니라 목표 부하를 걸었을 때 어떤 자원이 먼저 차는지를 재는 것. 자원 관점 점검은 USE(utilization·saturation·errors), 요청 관점은 RED(rate·errors·duration)로 구체화함.

이 저장소의 USE/RED 정리: computer_science/red_and_use_method/

2. 원리

이벤트 부하는 추세 외삽이 안 됨

SRE book은 수요 성장을 둘로 나눔 — 자연 성장(organic)과 이벤트성 성장(inorganic). 이벤트는 과거 그래프의 연장선에 없으므로, 근거는 추세가 아니라 산정과 실측임.

  • ① 예상 peak를 수치로 — 마케팅 도달 수 × 전환율, 과거 이벤트의 배수, 오픈 순간 집중도
    • "10배"는 하루 평균이 아니라 오픈 직후 수 분의 순간 RPS로 환산
  • ② 부하 테스트로 1대당 처리량 실측 — p95 latency가 꺾이는 지점이 그 인스턴스의 saturation point
  • ③ 필요 대수 = peak RPS ÷ 대당 처리량 + headroom — 1대가 죽어도 남은 대수로 견디는 N+1 이상

이 산식이 있어야 "몇 대가 필요한가"와 "지금 max 설정이 충분한가"에 숫자로 답할 수 있음.

2. 원리

판단 질문 — 이 병목은 나누면 나뉘는가

  • scale out이 답 — 요청을 나누면 병목도 나뉘는 경우
    • stateless API의 CPU·thread 포화. 전제는 상태 외부화(세션은 Redis, 파일은 S3)
  • scale up이 답 — 나눠도 나뉘지 않는 병목
    • 단일 요청의 처리 시간, 메모리 부족, DB 쓰기, 단일 hot key
    • 연결 수처럼 한도가 인스턴스 크기에 묶인 자원 (RDS max_connections)
  • up의 한계 — 가장 큰 인스턴스가 천장. 변경 순간 재시작·failover가 따라옴
  • out의 함정 — 앱을 늘리면 DB 연결·Redis 연결도 같이 늘어남. 병목이 이동함

그래서 순서는 스케일 방법 선택이 아니라 병목의 정체 확인이 먼저임.

4. 계층별 점검

ALB — 입구는 보통 병목이 아니지만

  • ALB는 트래픽에 따라 AWS가 자동으로 스케일함. 다만 점진적 — 초 단위 수직 스파이크가 예상되면 AWS 지원에 pre-warm을 요청할 수 있음
  • 볼 메트릭
    • RequestCount — traffic 신호. 이벤트 리허설 때 예상 peak와 비교할 기준
    • TargetResponseTime — 뒤 계층 latency의 합산 지표
    • HTTPCode_ELB_5XX_Count·RejectedConnectionCount — 보낼 대상이 없다는 신호. 대상 포화
  • 설정 점검 — idle timeout이 앱 keep-alive보다 짧은지, cross-zone 분산, 헬스체크 간격

ALB 메트릭은 병목의 위치를 알려주지 않음. 병목이 있다는 사실을 가장 먼저 알려줄 뿐 — 원인은 다음 계층들에서 찾음.

4. 계층별 점검

EC2·ASG — max가 진짜 한도인지 확인

  • 스케일 지표가 병목과 일치하는지 — CPU-bound 앱이면 ASGAverageCPUUtilization, 아니면 ALBRequestCountPerTarget이 정직함
    • thread 병목인데 CPU 지표로 스케일하면 지표가 안 올라 스케일이 안 됨
  • max 용량의 숨은 천장 — ASG max 뒤에 있는 계정 vCPU quota, 서브넷 여유 IP, (있다면) 라이선스 수
  • desired만 늘려보는 리허설 — 새 인스턴스가 InService까지 실제 몇 분 걸리는지 실측 (13장의 시간 벽)
  • scale in도 점검 — 이벤트 종료 직후 급감에서 한꺼번에 줄이면 남은 인스턴스가 다시 포화됨. cooldown·scale in 보호 확인

이 저장소의 ASG 예제: aws/auto_scaling_group/

4. 계층별 점검

Spring Boot — CPU보다 먼저 차는 것들

  • tomcat threads.max (기본 200) — busy thread가 먼저 포화되면 CPU가 남아도 응답이 밀림. 메트릭 tomcat_threads_busy_threads
  • HikariCP pool (기본 10) — hikari_connections_pending이 생기면 병목은 DB가 아니라 pool 크기일 수 있음. 단, pool을 키우기 전에 11장의 DB 연결 예산 먼저
  • JVM — heap 사용률·GC pause. 그리고 기동 직후 웜업 — JIT 컴파일 전에는 처리량이 낮음. 새 인스턴스가 투입 직후 느린 이유
  • timeout 체인 — client > ALB idle > app > DB 순으로 안쪽이 짧아야 함. 안쪽이 더 길면 바깥이 먼저 끊고 재시도 폭풍을 만듦

JVM 웜업 재현: computer_science/jvm_warmup/

4. 계층별 점검

Redis — 캐시가 무너지면 DB가 무너짐

  • maxmemory와 eviction policy — 이벤트 중 eviction이 돌기 시작하면 hit ratio가 떨어지고 miss가 RDS를 때림
  • hit ratio·연결 수 — 앱을 scale out하면 Redis 연결도 대수 × pool만큼 늘어남
  • hot key — 이벤트 상품 키 하나에 몰리는 부하는 샤딩으로 나뉘지 않음 → out이 아니라 로컬 캐시·복제로 풂
  • cache stampede — 같은 시각에 캐시가 만료되면 miss가 동시에 DB로 감
    • 대책 — TTL jitter(만료 시각 분산), 이벤트 오픈 전 캐시 warm-up, 요청 병합

Redis 점검의 결론은 Redis만의 문제가 아님 — 캐시의 포화는 곧 RDS의 부하 예고라서 11장과 함께 봐야 함.

4. 계층별 점검

RDS — 연결 예산이 scale out의 상한

  • max_connections은 인스턴스 메모리에 비례 — MySQL 기본 파라미터는 {DBInstanceClassMemory/12582880}. 즉 DB 스펙이 앱 연결 총량의 한도
    • 점검식 — 앱 최대 대수 × Hikari pool size + 운영·배치 연결 < max_connections
  • 읽기와 쓰기를 나눠서 판단 — 읽기는 read replica로 out, 쓰기는 instance class up만 가능
  • CPU·FreeableMemory·IOPS — gp 스토리지면 burst balance 소진 여부까지. Performance Insights로 이벤트 경로의 상위 쿼리 확인
  • 스펙 변경은 재시작·failover를 동반 — 이벤트 직전에 못 함. 한다면 며칠 전에 리허설과 함께

앱은 분 단위로 늘었다 줄지만 DB는 그러지 못함 — 그래서 DB 스펙 점검이 사전 점검의 본체임.

5. 판단

병목 신호 → 스케일 판단

  • EC2 CPU 포화 + stateless — scale out. 필요 대수는 4장의 산식으로
  • tomcat busy 포화, CPU 여유 — out 전에 threads.max와 뒤 계층 지연부터. thread를 다 쓰는 원인이 DB 대기면 out은 헛수고
  • Hikari pending 발생 — pool·DB 연결 예산 재설계. out 하면 DB 연결만 배수가 됨
  • Redis 메모리 압박 — node type up 또는 cluster로 샤딩 out. hot key만은 로컬 캐시로
  • RDS 읽기 CPU 포화 — read replica out + 앱의 읽기/쓰기 분리
  • RDS 쓰기·연결 포화 — instance class up. 이벤트 며칠 전에

공통 전제 — 신호는 부하 테스트로 미리 만들어 봄. 이벤트 당일에 처음 보는 신호가 없게 하는 것이 사전 점검의 목적임.

6. warm pool

초기화를 미리 치러 두는 풀

ASG 기능. 인스턴스를 미리 생성해 user_data까지 끝내 놓고, 트래픽은 받지 않는 상태로 대기시킴. scale out 때 새로 만들지 않고 풀에서 꺼내 시작함.

  • 대기 상태 세 가지
    • Stopped(기본) — 컴퓨팅 과금 없음, EBS·EIP만 과금. 꺼낼 때 재시작만 하면 됨
    • Running — 가장 빠르지만 대기 중에도 컴퓨팅 과금
    • Hibernated — 메모리를 EBS에 보존한 채 정지
  • min_size — 풀에 항상 유지할 대수. max_group_prepared_capacity로 상한 지정
  • reuse_on_scale_in — scale in 때 종료 대신 풀로 반환해 재사용
  • 초기화가 긴 인스턴스는 lifecycle hook으로 준비 완료 후에만 풀에 들어가게 보장

6. warm pool

terraform 설정과 확인

ASG에 붙이는 warm_pool 블록 — Stopped 2대를 항상 준비

resource "aws_autoscaling_group" "app" {
  # ...launch template, min 1 / max 4...
  warm_pool {
    pool_state = "Stopped"
    min_size   = 2
    instance_reuse_policy { reuse_on_scale_in = true }
  }
}

풀 상태와, scale out이 풀에서 꺼내 갔는지 확인

aws autoscaling describe-warm-pool --auto-scaling-group-name event-capacity-lab
aws autoscaling describe-scaling-activities --auto-scaling-group-name event-capacity-lab

activity 설명에 warm pool에서 시작했다는 문구가 남음 — cold launch와 InService 도달 시각을 비교하면 절약 폭이 보임.

7. 반전

warm pool이 데워 주지 않는 것

  • user_data는 풀에 들어가는 첫 부팅에 실행됨 — 재시작 때 다시 도는 초기화인지, 한 번이면 되는 초기화인지 스크립트를 확인해야 함
  • Stopped 풀은 프로세스가 죽어 있음 — 꺼내서 재시작하면 JVM은 cold. warm pool이 절약하는 것은 인프라 준비 시간이지 앱 웜업이 아님
    • 오픈 직후 새 인스턴스로 간 요청이 느린 이유는 여기 있음 — 웜업 트래픽·readiness 지연으로 따로 풂
  • DB에는 warm pool이 없음 — RDS·Redis의 수직 변경은 분 단위 + failover. 당일 대응 불가, 사전 작업임

결론 — warm pool은 시간 벽의 가운데 구간만 줄임. 나머지는 17장의 사전 전략이 맡음.

8. 사전 전략

시각을 아는 부하는 미리 채움

이벤트는 시작 시각을 앎 — 예측 불가 부하용 장치(반응형)에 기대지 않고 일정 기반으로 미리 올림.

scheduled action — 오픈 전 min·desired 상향, 종료 후 원복

resource "aws_autoscaling_schedule" "event_scale_out" {
  start_time       = "2026-08-01T02:30:00Z"  # 오픈 30분 전(UTC)
  min_size         = 3
  desired_capacity = 3
}
  • EC2 — 오픈 전 상향 + JVM 웜업 트래픽. target tracking과 warm pool은 예측이 틀린 부분의 보험
  • RDS·Redis — 스펙 변경·replica 추가는 며칠 전에, 부하 리허설과 함께
  • 캐시 — 이벤트 상품을 미리 적재(warm-up), TTL jitter로 동시 만료 방지

9. 트레이드오프

미리 키워두기 vs 반응형에 맡기기

미리 키워두기

  • 오픈 순간의 스파이크를 확실히 받음
  • 당일에 처음 보는 동작이 없음 — 리허설 가능
  • DB처럼 느린 계층과 보조를 맞출 수 있음

대가

  • 이벤트 전후의 유휴 비용
  • 예측이 크게 빗나가면 과잉·과소 프로비저닝
  • 원복을 잊으면 비용이 계속 샘 — scale in 일정까지가 계획

정답이 아니라 맥락. 시각을 아는 부하는 미리, 시각을 모르는 부하는 반응형 + warm pool. 대부분의 이벤트 대응은 이 둘의 조합이 됨.

10. 확인해 보기

스스로 점검 ①

Q1. 부하 테스트에서 p95가 폭증했다. CPU는 40%, hikari_connections_pending은 계속 증가. 먼저 할 일은?

  • 인스턴스를 2배로 scale out
  • pool 크기와 DB 연결 예산(앱 대수 × pool ≤ max_connections)을 확인
  • 인스턴스 타입을 한 단계 up

CPU가 낮은데 pending이 쌓임 — 병목은 CPU가 아니라 연결 경로. 이때 out을 하면 pool 총량이 배가 되어 DB 연결만 늘어남. 연결 예산과 쿼리 지연을 확인한 뒤에 스케일 방법을 정함.

10. 확인해 보기

스스로 점검 ②

Q2. Stopped warm pool을 도입해 InService까지는 빨라졌다. 그런데 이벤트 오픈 직후 새 인스턴스로 간 요청만 여전히 느리다. 원인은?

  • warm pool 인스턴스에서 user_data가 아예 실행되지 않았음
  • JVM 웜업은 트래픽을 받아야 진행됨 — warm pool은 앱 웜업을 대신 못 함
  • ALB 헬스체크 간격이 길어서 등록이 늦었음

Stopped 풀은 프로세스가 내려간 상태로 대기함. 꺼내면 JVM이 새로 뜨고 JIT 컴파일 전까지 처리량이 낮음. warm pool이 줄이는 것은 인프라 준비 시간이고, 앱 웜업은 웜업 트래픽이나 사전 투입으로 따로 풀어야 함.

11. 결론

도입 질문으로 돌아가서

"무엇을 점검할 것인가"의 답 — ① 예상 peak를 숫자로 만들고 ② 부하 테스트로 계층별 saturation 지점을 실측하고 ③ 병목마다 "나누면 나뉘는가"로 up/out을 정하고 ④ 시각을 아는 부하는 scheduled scaling·DB 사전 up·캐시 warm-up으로 미리 채움. warm pool과 target tracking은 예측이 틀린 부분을 받치는 보험임.

기억할 원리 — 스케일 방법 선택보다 병목의 정체 확인이 먼저고, 시각을 아는 부하는 미리 채워 둔다. 앱은 분 단위로 늘릴 수 있지만 DB는 그렇지 않다는 비대칭이 "사전" 점검의 이유임.
