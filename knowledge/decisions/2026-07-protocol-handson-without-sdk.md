## 결정

프로토콜 자체가 학습 대상인 핸즈온에서는 공식 SDK를 의존성으로 넣지 않고, 표준 라이브러리만으로 전송 계층과 양쪽 endpoint를 직접 만든다. 모델 호출이 필요한 자리에는 실제 모델 대신 정해진 순서만 수행하는 가짜 구현을 둔다.

ACP 핸즈온([computer_science/ai/acp-protocol/](../../computer_science/ai/acp-protocol/))이 이 방식으로 만들어졌다. 파이썬 표준 라이브러리만 쓰고, agent는 모델을 부르지 않으며, 환경변수 하나로 선 위의 원본 메시지를 stderr에 덤프한다.

## 이유

SDK를 쓰면 배우려던 것이 SDK 뒤로 숨는다. 메시지가 어떤 모양인지, 요청과 notification이 어떻게 구분되는지, 스트리밍이 별도 채널인지 아닌지가 전부 라이브러리 안에서 처리되어 관찰할 것이 남지 않는다.

부수 효과가 세 가지 더 있다. API key와 네트워크가 필요 없어 재현이 항상 성공한다. 모델을 부르지 않으므로 매 실행이 같은 줄을 내서 관찰 대상으로 적합하다. SDK 버전이 올라가도 핸즈온이 깨지지 않는다. ACP의 경우 공식 SDK 버전과 프로토콜 버전이 무관하게 움직이고 있어(Rust crate 2.x, Python 0.x, 둘 다 프로토콜 v1) 이 문제가 특히 크다.

대신 SDK가 대신해 주던 것을 직접 다뤄야 한다. 양방향 요청을 한 파이프에서 처리하는 부분이 그렇다. 여기서는 응답을 기다리는 동안 들어오는 메시지를 handler로 넘기는 loop 하나로 해결했다.

반대로 프로토콜이 수단일 뿐이고 그 위에 무엇을 만드는지가 학습 대상이면 이 결정은 적용하지 않는다. 그때는 SDK를 쓰는 편이 맞다.
