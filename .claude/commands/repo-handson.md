핸즈온 workspace를 만들거나, 이미 있는 핸즈온에 시나리오를 더한다. 대상 workspace(루트가 아닌 하위 디렉터리)와 주제는 `$ARGUMENTS` 전체에서 정하고, 인자가 없으면 대화 맥락에서 정한다. 인자는 자유 문장으로 오는 경우가 많아 위치 인자로 나누면 문장 조각이 경로가 된다.

- 인자에 `/`가 들어간 경로가 있으면 그것을 workspace로 쓰고, 없으면 인자 전체를 주제로 보고 경로를 정한다.
- 경로는 기존 구조를 따른다. 저장소 최상위 분류(`aws/`, `mlops/`, `computer_science/` 등) 아래에서 같은 종류의 핸즈온이 있는 곳을 찾아 그 옆에 둔다.
- 이미 있는 workspace면 먼저 `knowledge/index.md`와 `.claude/work/<branch>.md`를 읽는다. 버려진 방법을 다시 고르지 않기 위해서다.

## 핸즈온의 방향

사용자는 도구 사용법이 아니라 **시스템이 제공하는 기능**을 공부한다. 오픈소스와 서비스는 그 기능을 만드는 부품이다. "도구 X를 배운다"가 아니라 "기능 Y를 도구 X로 실험한다"로 쓴다. 이 방향이 모든 문서의 뼈대를 정한다.

- 독자는 그 분야 입문자인 실무 엔지니어다. 엔지니어 상식(셸, 컨테이너, kubectl)은 설명하지 않지만, 그 분야 고유의 용어는 처음 나올 때 정의한다.
- 핸즈온이 기능 여러 개를 다루면 첫 시나리오는 **기능 지도**다. 전체 기능을 mermaid 한 장으로 그리고, 기능마다 쓰는 도구와 시나리오 번호를 표로 잇는다. 로드맵 이미지를 함께 둔다.
- 시나리오 순서는 이야기로 정한다. 독자가 이미 아는 것에 빗댄 최종 목표를 먼저 보여 주고, "그것을 만들려면 무엇이 필요한가"로 거슬러 올라간다. 순서가 애매하면 사용자에게 묻는다.
- 같은 기능을 도구 두 개로 할 수 있으면 한 문서 안에서 도구마다 H2를 나눈다(`## <도구 A> 예제`, `## <도구 B> 예제`). 언제 어느 도구를 쓰는지 시점을 정해 쓴다.
- 도구마다 이름은 같은데 뜻이 다른 용어가 있으면 표로 나란히 놓고 차이를 못박는다.

## 순서

1. 다룰 기능과 시나리오 순서를 정하고, 단계가 3개를 넘으면 작업 상태 파일에 계획을 남긴다([workflow.md](../rules/workflow.md)).
2. workspace 아래 `docs/`에 시나리오 문서를 쓴다. 새 workspace면 `templates/knowledge/`를 복사하고 루트에 `AGENTS.md`를 만든다.
3. 실습 코드와 설정을 만든다. 도구가 여럿이면 코드 디렉터리를 도구별로 나눈다.
4. 실제 환경에서 모든 실습을 실행하고, 출력과 수치를 문서에 옮긴다.
5. 이미지를 만들고 mermaid를 렌더링해 검사한다.
6. 바뀐 결정과 겪은 문제를 knowledge와 troubleshooting에 남긴다.

## 시나리오 문서 구조

시나리오 문서 하나는 기능 하나다. 아래 순서를 지킨다. 실행 절차만 있고 "무엇이고 왜 필요한가"가 없는 문서는 쓰지 않는다.

1. `## 이 시나리오의 목표`: 표 하나. 행은 기능, 쓰는 도구, 입력, 작업(번호), 달성할 것.
2. **이 기능이 무엇인가**: 독자가 아는 것에 빗대고, 오해하기 쉬운 경계(이 기능이 다루는 것과 다루지 않는 것)를 정리한다.
3. `### 용어`: `| 용어 | 뜻 | 이 실습의 예 |` 표. 예 칸에는 실습의 실제 리소스 이름과 값을 쓴다.
4. **이 기능을 시스템이 제공해야 하는 이유**: 기능이 없을 때 생기는 문제를 근거로 든다. 실습에서 실제로 겪은 문제가 있으면 그것을 쓴다.
5. 대안 비교: 같은 일을 하는 다른 도구나 직접 구현하는 방식과 표로 비교한다.
6. `## 컴포넌트 역할`: 표.
7. `## 흐름`: mermaid.
8. `## 실습`(도구가 둘이면 도구별 H2): how-to. 배경 설명 없이 단계와 확인할 출력만 둔다.
9. `## 부록. 실무에서 얻는 것`: 이 실습을 해 봐야 알 수 있는 판단, 함정, 트레이드오프.
10. 외부 근거를 쓴 문서는 `## 참고 문서`에 번호 목록으로 링크한다.

사용자가 실무 관행을 물으면 웹에서 사례를 찾아 근거를 정리하고, 문서에 넣을 때는 참고 문서에 남긴다. 정해진 표준이 없으면 없다고 쓰고 많이 인용되는 문서를 알려 준다.

## docs 규칙

- 파일명 앞에 순서를 붙인다. 예: `1-problem.md`, `2-<기능>.md`. 순서를 바꾸면 파일명, 제목의 시나리오 번호, 모든 상대 링크, README 목차를 함께 고친다.
- `setup.md`를 따로 만들고 설치 관련 내용은 전부 여기에만 쓴다. 로컬 실습이면 up과 down을 한 줄 명령으로 만든다(`docker compose up -d`, `docker compose down -v`).
- 개인 장비를 쓰는 실습이면 장비를 다시 켠 뒤 환경을 되살리는 점검표를 따로 만든다. 무엇이 남고 무엇이 비는지 표로 먼저 쓴다.
- 본문은 `/akbun-writing:akbun-writing` 스킬로 쓴다. 스킬이 없는 환경이면 [philosophy.md](../rules/philosophy.md)와 루트 AGENTS.md의 문서 작성 규칙으로 쓰고 결과 보고에 남긴다.
- 작업 디렉터리에 의존하는 명령이 있으면 첫 코드블록에 `cd <workspace 경로>`를 넣거나 실행 위치를 단계에 적는다.
- markdown 규칙은 [.claude/rules/markdown.md](../rules/markdown.md)를 따른다.
- 개인 IP, 호스트 이름, 절대 경로, 실제 자격증명은 쓰지 않는다. `<서버 IP>` 같은 자리 표시를 쓴다.

## 실습 절차 형식

독자는 터미널이나 콘솔을 옆에 띄우고 한 줄씩 따라 한다. 지금 몇 번째 단계인지와 그 단계에서 무엇을 보면 되는지가 바로 보여야 한다.

- 단계는 `### 1. <할 일>` 또는 번호 목록으로 쓰고, 한 단계에 행동 하나만 담는다. 화면 메뉴와 버튼은 굵게 쓴다. 예: **Settings** → **Create**
- 그 단계에서 볼 결과(출력, 상태 값, 걸리는 시간)는 그 단계 바로 아래 `text` 코드블록이나 하위 bullet로 붙인다. 출력은 실제로 실행한 값을 쓴다.
- 실행마다 달라지는 값(ID, 시각, 버전 번호)은 달라진다고 적는다. 검증하며 미리 만든 리소스 때문에 독자의 결과가 달라지면 그 이유를 적는다.
- port-forward처럼 로컬 포트를 여러 개 쓰면 겹치지 않게 정하고 문서마다 같은 번호를 쓴다.

## 검증

- 모든 실습은 실제 환경에서 실행하고, 문서의 출력과 수치를 그 결과로 쓴다. 실행하지 못한 단계(화면 클릭 등)는 결과 보고에 검증하지 않았다고 남긴다.
- "동작한다"와 "맞다"를 구분한다. 오류 없이 응답해도 결과값이 기대값과 같은지 끝까지 대조한다.
- 실습 중 결정이 바뀌면 이미 쓴 계획 문서를 고치지 않고 `knowledge/decisions/`에 결과를 남긴다. 겪은 문제는 `docs/troubleshooting.md`에 증상과 해결방법으로 남긴다.
- GitOps 도구가 관리하는 리소스를 수동으로 고치면 되돌려진다. 수동으로 바꿀 리소스는 GitOps가 읽지 않는 별도 디렉터리로 분리한다.

## 이미지

- 사용자 스케치가 있으면 Codex CLI로 PNG를 만든다. 스타일은 사용자가 고른 `/akbun-draw:akbun-draw-explainer-svg` 스타일 토큰의 색과 선을 프롬프트에 옮기고, 스케치는 구도로만 쓴다. 스케치 종이의 줄이나 배경은 옮기지 않는다.

```bash
printf '%s' "<프롬프트>" | codex exec --sandbox workspace-write --skip-git-repo-check -C "$PWD" -i <스케치 경로> -
```

- 결과는 1920x1080으로 workspace의 `imgs/`에 새 파일로 저장한다. 크기가 다르면 `sips -z 1080 1920`으로 맞춘다. 사용자가 말하지 않으면 기존 이미지를 덮어쓰지 않는다.
- 로드맵 이미지는 30초~1분 안에 읽혀야 한다. 단계마다 짧은 제목 하나와 한 줄 설명, 선 아이콘 하나만 둔다. 후보를 여러 장 만들어 사용자가 고르게 하고, 고르지 않은 파일은 지운다.
- mermaid는 커밋 전에 렌더링해 확인한다. 엣지 라벨에 `@`, `:`, `/`가 있으면 따옴표로 감싼다.

```bash
PUPPETEER_EXECUTABLE_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" npx -y -p @mermaid-js/mermaid-cli@11.12.0 mmdc -i <블록>.mmd -o <블록>.svg
```

## knowledge 복사

새 workspace면 `templates/knowledge/`를 통째로 복사한다. workspace는 각각 독립이므로 자기 knowledge를 갖는다.

```bash
cp -R templates/knowledge "<workspace>/knowledge"
```

복사한 index.md와 log.md의 자리 표시 예시 줄은 첫 concept를 쓸 때 실제 항목으로 바꾼다.

## AGENTS.md

새 workspace 루트에 `AGENTS.md`를 만들고 다음을 담는다.

- 이 핸즈온이 무엇인지 한 줄.
- `@../../AGENTS.md`(루트까지의 상대 경로) 링크. 글로벌 규칙은 여기를 따른다.
- knowledge 포인터. 아래 문단을 그대로 넣는다.

```markdown
## knowledge

이 workspace의 결정 이유는 `knowledge/index.md`에 있다. 고치기 전에 읽고, 어긋나는 concept는 고치거나 지운다. 새로 얻은 결정과 절차는 같은 곳에 남긴다. 형식은 [.claude/rules/knowledge.md](../../.claude/rules/knowledge.md)를 따른다.
```

## 실습 환경

- 로컬로 충분하면 docker compose. `compose.yaml`을 workspace 루트에 둔다. compose까지 필요 없으면 macOS 기준 CLI 명령으로 대체한다.
- Kubernetes가 필요하면 manifest는 [kubernetes.md](../rule-details/kubernetes.md)를 따른다. 설치를 GitOps로 하면 사람이 직접 적용하는 manifest는 디렉터리를 나누고 manifests README 표에 그렇게 적는다.
- Python 실습 코드는 [python.md](../rule-details/python.md)를 따른다. 단독 스크립트는 PEP 723 머리와 `uv run`으로 의존성을 고정한다.
- 도구끼리 의존성이 충돌하면 가상환경을 나누고 그 이유를 문서와 knowledge에 남긴다.
- VM이 필요하면 AWS EC2 arm 인스턴스(t4g.medium)가 기본이다. x86을 요청하면 t3.medium과 x86 AMI로 바꾼다. terraform은 [terraform.md](../rule-details/terraform.md)를 따른다.

## 멈추는 지점

구현과 검증까지만 하고 commit, push, PR은 하지 않는다. 변경 요약과 검증하지 못한 것을 보고하고 멈춘다.
