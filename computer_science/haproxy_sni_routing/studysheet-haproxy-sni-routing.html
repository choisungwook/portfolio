암호화되기 전 한 조각 — HAProxy SNI 라우팅

키를 갖지 않은 L4 proxy가 도메인별로 백엔드를 나누는 원리와, 그 이름이 없을 때 벌어지는 일

이런 상황이 있다면 — 도메인별로 백엔드를 나눠야 하는데 인증서는 백엔드가 쥐고 있어서 proxy에서 TLS를 끝낼 수 없음. 게다가 IP로 들어오는 health check는 어디로도 안 감.

어떻게 풀까?

1. 문제 상황

이름으로 나누고 싶은데 안을 못 봄

이런 상황을 가정함.

  • a.example.com과 b.example.com을 서로 다른 백엔드로 보내야 함
  • 인증서와 키는 백엔드가 소유. proxy에 키를 복사할 수 없음(규정, 또는 mTLS 종단이 백엔드)
  • ✕ TCP proxy는 payload가 전부 암호문이라 Host 헤더를 못 읽음
  • ✕ IP로 붙는 health check와 옛 클라이언트는 이름 자체를 안 보냄

푸는 방법 중 하나 — handshake에서 아직 암호화되지 않은 첫 조각을 읽음. 거기에 이름이 있음.

2. 원리

ClientHello는 평문임

TLS는 첫 메시지부터 암호화되지 않음. 키를 아직 안 정했으니 당연함.

  • ① Client → Server ClientHello (평문) — 지원 버전, cipher, extension 목록
    • 여기에 server_name(SNI) extension이 들어 있음
  • ② Server → Client ServerHello + Certificate — 서버가 인증서를 고름
  • ③ 키 교환이 끝난 뒤부터 암호화. HTTP Host 헤더는 이 뒤에 나옴

즉 이름은 ②보다 먼저 지나감. 프록시가 키 없이 볼 수 있는 구간은 정확히 ①뿐임.

2. 원리

평문일 수밖에 없는 이유

보안 구멍이 아니라 순서 문제임.

  • 한 IP에 여러 도메인이 있으면 서버는 인증서를 고르기 전에 이름을 알아야 함
  • 이름을 암호화하려면 키가 필요하고, 키를 정하려면 인증서가 필요함 — 닭과 달걀
  • 그래서 RFC 6066은 이름을 ClientHello extension에 평문으로 실었음
  • 이 순서를 깨려고 나온 것이 ECH. 바깥 SNI는 공용 이름이 되고 진짜 이름은 암호화됨

SNI 라우팅은 이 설계의 부수 효과를 활용하는 것임. 원래 서버가 인증서를 고르라고 만든 필드를 proxy가 대신 읽음.

2. 원리

SNI는 라우팅 키이지 신원이 아님

  • SNI 값은 클라이언트가 마음대로 쓰는 문자열. 아무도 검증하지 않은 상태로 읽음
  • 인증서 검증은 그 뒤에 클라이언트와 백엔드 사이에서 따로 일어남
  • passthrough에서는 proxy가 SNI와 Host 헤더가 같은지 비교할 수 없음 — Host는 암호문 안에 있음

그래서 SNI로 하는 것은 dispatch지 authorization이 아님. 접근 제어가 필요하면 handshake 이후에 할 수 있는 자리(TLS 종단, mTLS, 앱)에서 해야 함.

SNI와 Host를 다르게 보내는 domain fronting류 기법이 성립하는 이유도 이 지점임.

2단계. tcp-request inspect-delay가 연결을 잡아 둠. 이게 없으면 버퍼가 비어 있어 판단할 게 없음.

3
client
→
HAProxyreq.ssl_sni = a.lab.local
→

3단계. 버퍼가 ClientHello면(req.ssl_hello_type 1) SNI를 꺼내 backend를 고름. 복호화는 없음.

4
client
→
HAProxy바이트만 전달
→
backend여기서 TLS 종단

4단계. 이후로는 그냥 TCP. handshake는 client와 backend가 끝냄. 키는 백엔드에만 있음.

3. 구조 이해하기

설정은 네 줄로 끝남

passthrough frontend — 이름을 읽어 backend만 고르고 TLS는 건드리지 않음

frontend fe_sni_passthrough
  bind *:8443
  mode tcp
  tcp-request inspect-delay 5s          # 첫 조각을 기다림
  tcp-request content accept if { req.ssl_hello_type 1 }
  tcp-request content reject                # TLS가 아니면 버림

  use_backend be_a if { req.ssl_sni -i a.lab.local }
  use_backend be_b if { req.ssl_sni -i b.lab.local }
  use_backend be_nosni if !{ req.ssl_sni -m found }
  default_backend be_unknown

req.ssl_sni는 request 버퍼가 살아 있을 때만 유효함. 로그에 남기려면 set-var(sess.sni)로 복사해 두고 %[var(sess.sni)]로 찍음. TLS를 종단하는 frontend에서는 같은 값을 ssl_fc_sni로 읽음.

4. 확인 문제

확인 문제 1

mode tcp frontend에서 inspect-delay를 지우면 어떻게 되는가?

  • SNI 매칭이 느려질 뿐 결과는 같다
  • 버퍼가 빈 채로 규칙이 평가돼 SNI 조건이 맞지 않고 default_backend로 감
  • HAProxy가 설정 오류로 기동에 실패한다
  • HAProxy가 TLS를 종단해서 SNI를 읽는다

연결 수립 직후에는 payload가 아직 안 왔음. inspect-delay는 "기다리는 시간"이 아니라 판단할 재료를 모으는 시간임.

5. SNI가 없는 handshake

이름을 안 보내는 클라이언트는 정상임

server_name은 선택 extension임. 없는 handshake도 규격에 맞음. 클라이언트 버그로 취급하면 원인을 못 찾음.

  • IP로 접속 — RFC 6066이 IP 리터럴을 금지함. 올바른 클라이언트일수록 extension을 뺌 (가장 흔함)
  • health check와 모니터링 probe — 대개 이름이 아니라 주소로 붙음
  • openssl s_client — -servername을 안 주면 SNI 없음
  • 옛 스택 — XP 시절 브라우저, Java 6, Android 2.x
  • ECH — 진짜 이름이 암호화됨. 바깥 SNI는 공용 이름이라 테넌트 키로 못 씀

에지에서 "가끔 아무 데나 간다"는 신고는 대부분 이 목록 중 하나임.

5. SNI가 없는 handshake

"없음"과 "모르는 이름"은 다른 사건임

req.ssl_sni는 빈 문자열이 아니라 정의되지 않은(undefined) 샘플임. 값 비교는 그냥 안 맞고, 둘 다 default_backend로 흘러감.

-m found는 값이 아니라 존재 여부로 매칭 — 두 경우를 갈라 놓는 한 줄

  use_backend be_nosni if !{ req.ssl_sni -m found }   # 이름을 안 보냄
  default_backend be_unknown                       # 모르는 이름

가르는 이유는 라우팅이 아니라 운영임. 둘은 원인도 대응도 다름.

  • 이름 없음 → IP로 붙는 probe거나 옛 클라이언트. 대개 우리 쪽 설정 문제
  • 모르는 이름 → 오래된 DNS, 삭제된 테넌트, 스캐너. 대개 저쪽 문제

5. SNI가 없는 handshake

답은 넷 중 하나임

받아 준다

  • fallback backend — default_backend로 흡수. 그 백엔드가 클라이언트가 받아들일 인증서를 쥐고 있어야 함
  • 전용 no-SNI backend — 위와 같지만 로그·stats에서 원인이 갈림
  • TLS 종단 — 기본 인증서를 주고, 그 다음 Host 헤더로 라우팅. 클라이언트가 SNI는 안 보내도 Host는 보냄

끊는다

  • reject — tcp-request content reject unless { req.ssl_sni -m found }
  • IP health check가 같이 죽음
  • 옛 클라이언트가 조용히 사라짐
  • 클라이언트를 전부 통제할 때만 고를 수 있음

질문 자체를 없애는 다섯 번째도 있음 — 테넌트마다 포트나 IP를 분리하고 dst_port로 라우팅. 수가 적으면 이게 제일 단순함.

6. IP로 HTTPS 하기

IP 접속은 문제가 두 개임

https://10.0.0.5 하나에 서로 다른 고장이 겹쳐 있음. 고치는 자리도 다름.

  • ① 라우팅 — SNI가 없어서 proxy가 고를 근거가 없음 → fallback 경로가 필요
  • ② 검증 — 클라이언트가 인증서에서 IP SAN을 찾음 → 인증서에 IP를 넣어야 함

요즘 클라이언트는 CN을 보지 않음. CN=127.0.0.1은 소용없고 subjectAltName에 IP:127.0.0.1이 있어야 함. 핸즈온의 fallback 인증서는 그래서 DNS:default.lab.local, IP:127.0.0.1로 발급함.

공인 CA는 사설 IP에 IP SAN을 발급하지 않음. 사내에서 IP로 HTTPS를 하겠다면 사설 CA를 세우거나, 클라이언트가 검증을 건너뛰는 것을 받아들이는 선택이 됨.

6. IP로 HTTPS 하기

passthrough와 종단, 각각의 답

종단 frontend — crt-list의 첫 줄이 기본 인증서. SNI가 없으면 이것이 나감

bind *:8444 ssl crt-list /usr/local/etc/haproxy/crt-list.txt

# crt-list.txt
/certs/bundles/default.pem      # ← 기본. IP SAN 보유
/certs/bundles/a.lab.local.pem
/certs/bundles/b.lab.local.pem

# handshake 후에는 평문 HTTP — 이름은 Host에서 얻음
acl host_a req.hdr(host),field(1,:) -i a.lab.local
  • passthrough(8443) — 이름이 없으니 fallback backend로. 인증서 문제는 그 백엔드가 해결
  • 종단(8444) — 기본 인증서로 handshake를 성사시킨 뒤 Host로 라우팅. proxy가 키를 쥐는 대가

6. IP로 HTTPS 하기

strict-sni는 무엇을 바꾸는가

bind ... ssl crt-list ... strict-sni를 붙이면 매칭되는 인증서가 없을 때 handshake를 거절함. SNI가 아예 없는 경우도 포함임.

켤 때

  • 테넌트가 많고, 엉뚱한 기본 인증서가 나가는 것 자체가 사고인 에지
  • 기본 인증서를 아무에게나 보여 주지 않음

대가

  • IP로 붙는 health check가 전부 실패
  • 옛 클라이언트가 handshake 단계에서 끊김
  • 실패가 HTTP 상태 코드가 아니라 TLS 오류로 나와 디버깅이 어려움

정답은 상황에 있음. probe에 진짜 hostname을 줄 수 있으면 켜고, 못 주면 기본 인증서를 남겨 둠.

4. 확인 문제

확인 문제 2

사내 모니터링이 https://10.0.0.5 로 health check를 보내는데, 에지에 strict-sni를 켰다. 무엇이 관측되는가?

  • 404가 늘어난다
  • 기본 인증서로 응답하고 default_backend로 간다
  • TLS handshake 단계에서 실패한다. HTTP 로그에는 아무것도 안 남는다
  • SNI가 IP 문자열로 채워져 라우팅된다

IP 접속은 SNI를 안 보내고, strict-sni는 매칭 실패를 거절로 처리함. 요청이 HTTP까지 도달하지 못하므로 httplog에는 흔적이 없음. 이때 필요한 것이 ssl_fc_has_sni 같은 필드임.

7. 정리

남길 것

  • SNI 라우팅이 되는 이유는 ClientHello가 평문이기 때문이고, 그건 서버가 인증서를 고르려면 이름이 먼저 필요해서임
  • HAProxy는 inspect-delay로 그 첫 조각을 기다린 뒤 req.ssl_sni로 고름. 복호화도 키도 없음
  • 읽은 이름은 검증되지 않은 값임. dispatch에 쓰고 authorization에는 쓰지 않음
  • SNI 없는 handshake는 정상임. -m found로 "없음"과 "모르는 이름"을 갈라 두면 장애 분석이 달라짐
  • IP로 HTTPS는 라우팅(fallback)과 검증(IP SAN) 두 군데를 같이 손봐야 함
