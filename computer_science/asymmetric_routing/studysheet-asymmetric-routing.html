가는 길과 오는 길이 다를 때 — 비대칭 라우팅

라우팅은 방향마다 따로 정해진다. 그것을 모르고 만든 장비가 문제를 일으킨다

이런 상황이 있다면 — 방화벽 로그에는 요청이 찍히는데 응답이 안 돌아옴. 서버 tcpdump에는 SYN도 SYN-ACK도 다 보임.

패킷은 어디서 사라졌을까?

1. 문제 상황

양쪽 다 "우리 쪽은 정상"이라고 말함

회선을 이중화하거나 VPC를 여러 개 연결한 뒤에 자주 나오는 증상.

  • 서버에서 tcpdump하면 요청도 응답도 정상. 서버 담당자는 "우리는 응답 보냈다"
  • ✕ 클라이언트에서는 SYN만 계속 재전송되고 응답이 없음
  • ✕ 어제까지 되던 게 라우팅 한 줄 바꾼 뒤 안 됨. 방화벽 설정은 그대로
  • ✕ ping은 되는데 TCP만 안 되는 경우도 있고, 그 반대도 있음

푸는 방법 중 하나 — "패킷이 어디서 죽었나"가 아니라 "가는 길과 오는 길이 같은가"부터 확인.

2. 원리

IP는 방향마다 따로 판단함

라우터는 패킷을 하나씩 보고 목적지만으로 다음 홉을 정함. 이 패킷이 어떤 대화의 일부인지 묻지 않음.

  • 클라이언트의 라우팅 테이블이 가는 길을 정함
  • 서버의 라우팅 테이블이 오는 길을 정함
  • 둘은 서로를 참조하지 않음. 같은 길이 되는 건 보장이 아니라 우연

그래서 비대칭 라우팅은 고장이 아니라 기본 성질임. 대칭이 유지되던 건 경로가 하나뿐이었기 때문임.

여기까지가 이 학습의 절반. 나머지 절반은 "그런데 왜 어떤 환경에서는 깨지는가"임.

2. 원리

경로가 둘 이상이면 언제든 생김

아래 조건 중 하나만 있어도 비대칭이 만들어질 수 있음.

  • NIC이 두 개인 호스트 — 들어온 인터페이스와 나가는 인터페이스가 다름
  • 회선 이중화 — Direct Connect와 VPN, 또는 ISP 두 곳
  • 서로 다른 라우팅 테이블 — 우리 쪽은 peering, 상대 쪽은 transit gateway
  • ECMP와 해시 — 방향마다 다른 경로가 선택됨
  • AZ마다 배치된 어플라이언스 — 가는 길과 오는 길이 다른 AZ의 장비를 탐

공통점은 어느 쪽도 잘못 설정된 게 아니라는 것. 각자 자기 테이블대로 최선의 경로를 골랐을 뿐임.

2. 원리

깨뜨리는 것은 라우팅이 아니라 상태

비대칭 자체는 통신을 막지 않음. 한쪽 길에만 상태를 기억하는 장비가 있을 때 막힘.

  • conntrack, stateful 방화벽 — SYN을 못 본 장비에게 SYN-ACK는 소속 없는 패킷
  • NAT — 매핑을 만든 장비를 우회해서 돌아오면 되돌릴 주체가 없음
  • rp_filter — 출발지 주소로 되돌아갈 경로가 없거나 다른 인터페이스면 커널이 버림
  • 클라우드의 출발지 검사 — ENI는 자기 주소가 아닌 출발지의 패킷을 못 보냄

진단 순서가 여기서 나옴 — 경로가 갈리는 지점을 찾고, 그 두 경로 중 한쪽에만 있는 상태 장비를 찾음.

4. rp_filter

모드 하나 차이로 결과가 갈림

커널이 들어온 패킷의 출발지 주소로 라우팅 테이블을 거꾸로 조회함. RFC 3704의 구현.

실효값은 all과 인터페이스 설정 중 큰 값. 한쪽만 꺼도 안 꺼짐

# rp_filter = max(conf.all.rp_filter, conf.<dev>.rp_filter)
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.eth1.rp_filter
  • 0 (off) — 검사 안 함
  • 2 (loose) — 출발지로 가는 경로가 아무 인터페이스로든 있으면 통과
  • 1 (strict) — 되돌아갈 경로가 들어온 그 인터페이스여야 통과

비대칭 경로가 있는 곳에서 strict는 정상 트래픽을 버림. RFC 3704가 그런 위치에 loose를 권하는 이유임.

5. 로컬 실습

컨테이너 네 개로 재현

서버를 dual-home으로 두면 두 번째 경로가 공짜로 생김. 오는 길만 바꾸면 됨.

토폴로지 — 가는 길은 client의 route로 r1에 고정

                 edge 10.10.0.0/24
client .10 ──┬── r1 .2 ── net_a 10.20.0.0/24 ── .10 server
             └── r2 .3 ── net_b 10.30.0.0/24 ── .20

# 오는 길을 r2로 넘김 = 비대칭 완성
docker exec ar-server /scripts/return-path.sh r2

관찰 도구. tcpdump는 라우팅 판단 이전에 찍히므로, 버려지는 패킷도 들어오는 건 보임. "보이는데 안 나감"이 곧 커널이 버렸다는 증거.

5. 로컬 실습

조건을 하나씩 얹은 결과

통신됨

  • 대칭 — 기준선
  • 비대칭, 상태 장비 없음
  • 비대칭 + rp_filter loose + 역경로 존재
  • 비대칭 + r1에서 MASQUERADE

끊김

  • 비대칭 + rp_filter loose, 역경로 없음
  • 비대칭 + rp_filter strict (역경로 있어도)
  • 비대칭 + stateful 방화벽

주의할 기본값. 리눅스는 nf_conntrack_tcp_loose=1이 기본이라 SYN을 놓친 흐름도 주워 담음. 그래서 평범한 리눅스 라우터에서는 비대칭이 조용히 숨겨짐. 방화벽 제품은 이걸 꺼 두므로 그때 드러남.

6. 해법

경로를 맞추거나, 주소를 바꾸거나

① 라우팅을 대칭으로

  • 양쪽 테이블이 같은 경로를 가리키게 함
  • 출발지 주소가 보존됨
  • 상대 조직의 협조가 필요함

② NAT으로 강제

  • 출발지를 바꾸면 응답은 그 장비로 올 수밖에 없음
  • 상대는 경로 한 줄만 추가하면 됨
  • 상대가 클라이언트를 주소로 구분 못 함

다중 NIC 호스트에서는 policy routing이 ①의 형태임. ip rule add from <그 인터페이스 주소> lookup <그 테이블>

NAT은 대칭을 사 오는 것이고, 그 값은 출발지 식별. AWS 실습이 이 거래를 그대로 보여줌.

7. AWS

VPC는 상태를 안 보지만 두 가지를 막음

VPC 라우팅 자체는 stateless라, 경로가 갈린다는 이유로 패킷을 버리지는 않음. 대신 이 둘이 걸림.

  • 출발지 검사 — ENI는 자기 주소가 아닌 출발지의 패킷을 내보내지 못함. 다중 ENI 인스턴스가 여기 걸림
  • 없는 경로 — 상대 VPC에 우리 대역으로 가는 route가 없으면 응답이 갈 곳이 없음
  • Security group은 ENI 단위 stateful이지만, 양방향이 같은 ENI를 쓰므로 보통 원인이 아님

AL2023은 amazon-ec2-net-utils가 두 번째 ENI용 policy routing 규칙을 자동으로 만들어 둠. 실습은 그 규칙을 지워서 원래 동작을 확인함.

7. AWS

private NAT gateway가 실제로 한 일

라우팅 테이블을 고친 게 아님. 질문을 바꿈.

  • 전 — "우리 VPC 대역 전체를 되돌려 줄 수 있습니까"
  • 후 — "우리가 고른 작은 대역 하나만 되돌려 줄 수 있습니까"

그래서 100.64.0.0/10(RFC 6598)을 secondary CIDR로 쓰는 패턴이 반복됨. 상대 네트워크와 겹칠 확률이 가장 낮은 대역이라 승인받기 쉬움.

대역이 실제로 겹쳐서 peering 자체가 불가능한 경우에도 같은 원리가 쓰임. 그때는 transit gateway가 경로를 나름.

EIP가 없는 NAT gateway라는 점만 다름. 로컬 실습의 MASQUERADE 한 줄과 하는 일이 같음.

8. 트레이드오프

대칭을 사면 병목을 얻음

얻는 것

  • 오는 길이 한 곳으로 확정됨
  • 상대 조직이 바꿀 설정이 route 한 줄로 줄어듦
  • 대역이 겹쳐도 연결할 수 있음

잃는 것

  • 상대가 클라이언트를 주소로 구분 못 함
  • NAT이 stateful 병목이자 단일 장애 지점
  • 포트 고갈과 처리 비용이 새로 생김

어디를 봐야 하나. "비대칭을 없앨까"가 아니라 "이 경로 위에 상태를 가진 장비가 있는가". 없으면 비대칭인 채로 둬도 됨.

9. 확인해 보기

스스로 점검 ①

Q1. 서버 tcpdump에는 SYN과 SYN-ACK가 모두 보이는데 클라이언트는 응답을 못 받는다. 가장 먼저 배제할 수 있는 원인은?

  • 서버 쪽 인바운드 방화벽 정책
  • 서버가 응답을 내보내는 경로
  • 돌아오는 경로 위의 stateful 장비

인바운드가 막혔다면 SYN이 서버까지 도달하지 못함. SYN이 도착했고 서버가 SYN-ACK까지 만들었다는 것은 인바운드 통과의 증거임. 그래서 남는 후보는 돌아오는 경로뿐임.

9. 확인해 보기

스스로 점검 ②

Q2. 리눅스 라우터 두 대로 비대칭을 만들었는데 통신이 잘 된다. 실제 방화벽에서는 끊긴다면 무엇이 달랐는가?

  • 리눅스 라우터에 rp_filter가 켜져 있었다
  • 리눅스 기본값인 nf_conntrack_tcp_loose=1이 중간부터 흐름을 주워 담았다
  • 리눅스는 conntrack을 아예 쓰지 않는다

loose 모드는 SYN을 못 본 흐름도 ESTABLISHED로 받아들여 비대칭을 숨김. 0으로 바꾸면 SYN-ACK가 INVALID가 되어 방화벽 제품과 같은 증상이 재현됨. rp_filter가 켜져 있었다면 리눅스 쪽에서도 이미 끊겼을 것임.

10. 결론

도입 질문으로 돌아가서

패킷은 사라진 게 아니라 다른 길로 갔고, 그 길 위의 장비가 자기가 모르는 패킷이라 버린 것임. 라우팅은 원래 방향마다 따로 정해지므로 비대칭은 고장이 아님. 고장은 그 두 경로 중 한쪽에만 상태를 가진 장비를 놓았을 때 생김.

기억할 원리 — 상태를 가진 장비는 양방향을 모두 지나야 한다. 그것을 라우팅으로 맞추면 주소가 보존되고, NAT으로 맞추면 협의 비용이 줄지만 출발지 식별을 잃음. 어느 쪽이든 먼저 할 일은 두 방향의 경로를 그려 보는 것임.
