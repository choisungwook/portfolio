멀티턴 대화 — 모델은 왜 잊는가

LLM API로 챗봇을 만드는 사람을 위한, 대화가 실제로 어디에 쌓이는지 확인하는 학습지

이런 상황이 있다면 — 사용자가 "내 이름은 악분이야"라고 말한 바로 다음 턴에 "내 이름이 뭐야?"를 물었는데, 챗봇이 모른다고 답함. 에러 로그도 없음

어떻게 풀까?

1. 문제 상황

한 턴 만에 이름을 잊는 챗봇

이런 상황을 가정함

같은 프롬프트를 채팅 UI에 붙여넣으면 잘 동작함. 코드로 부르면 안 됨.

  • ✕ 턴 2에서 이전 턴 내용을 전혀 모름
  • ✕ 예외도 에러 코드도 없음. HTTP 200에 정상 응답
  • ✕ 프롬프트를 고쳐도 그대로임 — 프롬프트 문제가 아님

임시방편으로 "이전 대화를 기억해"를 프롬프트에 넣어도 소용없음. 기억할 대상이 요청 본문에 없기 때문.

푸는 방법 중 하나 — 모델을 고치지 않고, 애플리케이션이 지난 메시지를 모아 매 호출마다 다시 보냄

2. 원리

API는 상태를 갖지 않도록 설계됨

POST /v1/messages와 POST /v1/chat/completions는 평범한 stateless HTTP 엔드포인트임. 요청 본문이 입력 전부, 응답이 출력 전부.

  • 세션 쿠키 없음, connection affinity 없음, 서버 측 버퍼 없음
    • 턴 2 요청이 도착할 때 턴 1을 붙들고 있는 주체가 없음
  • 왜 이렇게 설계했나 — 서버가 대화를 들고 있으면 요청을 아무 인스턴스에나 보낼 수 없음
    • 상태를 버리면 수평 확장·재시도·장애 격리가 전부 단순해짐

다른 곳에도 적용됨. HTTP 자체, REST, JWT 인증, stateless pod — 상태를 호출자나 외부 저장소로 밀어내는 같은 설계.

2. 원리

멀티턴은 모델의 성질이 아니라 배열의 길이

섞이기 쉬운 두 정의를 나눠야 함.

  • 사용자 관점 — 여러 번 주고받고, 뒤 질문이 앞 대화에 기댈 수 있는 경험
  • API 관점 — messages 배열이 커지는 것. 턴 3은 턴 1·2를 그대로 다시 실어 보냄

뒤가 앞을 만들어 냄. 제3의 무언가는 없음. "멀티턴 모델"이라는 것도 없고, 입력을 더 보내는 호출자만 있음.

턴 3에서 실제로 나가는 요청 본문 (앞 두 턴이 전부 다시 실림)

messages = [
  {"role": "user",      "content": "내 이름은 악분이야"},   # 턴 1
  {"role": "assistant", "content": "네, 기억하겠습니다"},  # 턴 1 답
  {"role": "user",      "content": "내 이름이 뭐야?"},     # 턴 2
  {"role": "assistant", "content": "악분이라고 하셨습니다"},
  {"role": "user",      "content": "몇 번 물어봤지?"},     # 턴 3 ← 새 질문은 이것뿐
]

배열을 프로세스 안에 두면 재시작·다중 pod에서 사라짐. 저장소는 API 호출 바깥에 붙음.

1단계 — 잊는 것을 눈으로 확인

호출 2번. 두 번째는 첫 번째만 아는 것을 물음

# openai/01_stateless.py — 매 호출 messages 길이 1
client.chat.completions.create(model=MODEL,
    messages=[SYSTEM, {"role": "user", "content": "내 이름은 악분이야"}])
client.chat.completions.create(model=MODEL,
    messages=[SYSTEM, {"role": "user", "content": "내 이름이 뭐야?"}])  # 앞 호출과 무관

기대 결과

turn 1 > 네, 악분님. 기억하겠습니다.
turn 2 > 죄송하지만 이전에 이름을 알려주신 적이 없습니다.

체크포인트. 모델 실패가 아님. 주어진 입력에 대해서는 정확한 답이며, 그 입력에 히스토리가 없었을 뿐임.

2단계 — 히스토리를 다시 보냄

모델 설정은 그대로. history만 누적

# openai/02_multi_turn.py
history.append({"role": "user", "content": question})

history.append({"role": "assistant", "content": answer})  # 답도 누적

기대 결과 — prompt token이 함께 오름

turn 1 > 네, 악분님. 기억하겠습니다.
  [3 messages sent, 68 prompt tokens]
turn 2 > 악분이라고 하셨습니다.

체크포인트. 기억은 호출자가 만든 것. 1단계와 2단계 사이에 바뀐 모델 설정은 하나도 없음.

4. 핸즈온

2단계 확인 — provider를 바꿔도 루프는 같음

openai/(gpt-5.6-luna)와 claude/(claude-sonnet-5)는 파일 이름·순서가 같고, 같은 번호는 같은 개념임. append → 전송 → append 루프도 동일함. 규격 차이는 세 군데뿐.

  • system 프롬프트 — OpenAI는 messages[0], Anthropic은 별도 system 필드
  • 응답 본문 — OpenAI는 choices[0].message.content 문자열, Anthropic은 block 리스트에서 type == "text"만 추림
  • 출력 상한 — GPT-5 계열은 max_completion_tokens, Anthropic은 max_tokens

같은 자리, 다른 규격

# openai/02  messages=[SYSTEM] + history
# claude/02  system=SYSTEM, messages=history

체크포인트. 바뀐 것은 요청 모양뿐이고, 누적 로직은 provider와 무관함.

4. 핸즈온

4단계 — 서버는 캐시하지만 기억하지는 않음

"LLM 서버단에서도 캐시한다"가 사실인 지점이자, 오해가 생기는 지점. 캐시 API가 provider마다 달라 04만 두 디렉터리에서 다름.

기대 결과 — claude/04_prompt_cache.py, 같은 1000+ 토큰 system 프롬프트를 두 번 보냄

call 1  uncached=14 cache_write=1543 cache_read=0
call 2  uncached=14 cache_write=0    cache_read=1543
  • 맞는 해석 — 서버가 그 prefix의 내부 연산 결과를 이미 갖고 있어 재계산을 건너뜀. 값이 약 1/10로 떨어짐
  • 틀린 해석 — 서버가 대화를 들고 있음. call 2도 prefix 전체를 다시 전송했음. 캐시 키가 보낸 바이트 자체이며 prefix 일치라, 한 글자만 달라도 뒤가 전부 무효화됨

OpenAI는 자동 캐시라 선언 없이 usage.prompt_tokens_details.cached_tokens로 확인함. Anthropic은 명시적 캐시라 cache_control로 prefix 끝을 표시해야 함.

체크포인트. prompt caching은 히스토리를 다시 보내는 비용을 줄이는 것이지, 다시 보내는 일을 없애는 것이 아님.

5. 실제 제품이 푸는 방식

stateless가 항상은 아님

  • Claude Code — 로컬 append-only JSONL. ~/.claude/projects/<cwd-slug>/<session-uuid>.jsonl
    • 한 줄에 JSON 객체 하나, 각 항목이 parentUuid로 앞 항목에 연결됨. --resume이 이 파일을 다시 읽어 재생. 4단계의 jsonl 저장소와 같은 구조
  • OpenAI — 두 가지를 다 제공
    • Chat Completions: stateless. 위 실습과 동일
    • Responses API: stateful. store: true로 보내고 응답 id를 다음 호출의 previous_response_id로 넘기면 히스토리를 다시 안 보내도 됨
  • Anthropic — Messages API는 stateless로 유지하고, 서버 측 상태는 Managed Agents라는 별도 제품에 둠(세션이 서버에 살고 message 배열 대신 event를 주고받음)

정확한 규칙은 "LLM API는 stateless"보다 좁음 — Chat Completions·Messages는 호출자가 누적, Responses·Managed Agents는 서버가 누적.

6. 확인해 보기

스스로 점검

Q1. 20턴째 대화 중이고 각 턴이 약 500 토큰임. 20턴째 요청의 input token은 대략 얼마인가?

  • 약 500 — 새 질문만 과금됨
  • 약 10,000 — 앞 19턴이 전부 다시 실림
  • 약 1,000 — 직전 턴까지만 실림

매 턴이 전체 히스토리를 재전송하므로 input이 턴 수에 비례해 누적됨. 컨텍스트 한계와 비용이 같은 이유에서 생김.

Q2. system 프롬프트에 datetime.now()를 넣었더니 cache_read가 계속 0임. 이유는?

  • 토큰 수가 최소 캐시 길이에 못 미침
  • 캐시 TTL이 만료됨
  • prefix 바이트가 매 요청 달라져 prefix 일치가 안 됨

캐시 키는 보낸 바이트이고 prefix 일치임. 앞쪽이 한 글자만 바뀌어도 그 뒤 전체가 무효화됨. 변하는 값은 마지막 breakpoint 뒤로 옮겨야 함.

7. 트레이드오프

누적-재전송 방식이 주고받는 것

얻는 것

  • 전체 transcript를 직접 열람·수정 가능
  • provider 간 이식 가능. 벤더 종속 없음
  • 구현이 리스트 하나. 디버깅이 쉬움

잃는 것

  • input 토큰이 세션 길이의 제곱에 가깝게 증가
  • 컨텍스트 한계에서 요약·절삭 필요. 무손실 아님
  • 보관·삭제·접근제어가 전부 앱 책임

언제 쓰는가. 대부분의 시스템에서 기본값. transcript 감사·수정·이전이 필요하면 필수.

언제 쓰지 않는가. 대화가 매우 길고 클라이언트가 얇으며 벤더 종속을 감수할 수 있으면 서버 측 상태(previous_response_id, Managed Agents)가 나음.

8. 결론

이름을 잊던 챗봇으로 돌아가서

버그는 프롬프트가 아니라 두 번째 요청의 본문에 있었음. 엔드포인트가 stateless라 턴 1을 붙들고 있는 주체가 없었고, 앱이 히스토리를 실어 보내자 그대로 해결됨.

기억할 원리 한 문장 — 대화는 모델이 가진 것이 아니라 호출자가 매번 다시 만드는 것.

  • 다음에 응용할 지점
    • 컨텍스트가 찼을 때의 요약·compaction 전략
    • prompt caching을 깨지 않는 프롬프트 배치(변하는 값을 뒤로)
    • 세션 저장소를 파일에서 DB로 옮길 때의 보관·삭제 정책
