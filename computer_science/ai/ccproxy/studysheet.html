ccproxy로 배우는 AI proxy

Claude Code 앞에 proxy를 세워, 무엇을 얻고 무엇이 위험해지는지 직접 확인하는 학습지

이런 상황이 있다면 — Claude Code는 Anthropic API 하나만 볼 줄 아는데, 팀은 사내 gateway와 싼 모델로 붙이라고 함. 클라이언트 코드는 못 고침.

어떻게 풀까?

1. 문제 상황

클라이언트는 한 가지 API만 알고, 백엔드는 바뀌어야 함

이런 상황을 가정함

Claude Code는 Anthropic Messages API 포맷으로만 요청함. 붙일 백엔드는 OpenAI 호환 사내 endpoint.

  • ✕ 클라이언트 closed source — 요청 포맷 변경 불가
  • ✕ 백엔드 스키마를 Anthropic 형태로 바꾸는 것도 불가
  • ✕ 짧은 질문까지 큰 모델로 나가 비용 통제 안 됨

푸는 방법 중 하나 — 사이에 Anthropic API를 흉내내는 proxy를 세움. ccproxy 계열 도구의 자리.

2. 원리

클라이언트가 목적지를 환경변수로 노출함

요청 주소를 ANTHROPIC_BASE_URL에서 읽음. fork 없이 목적지 교체 가능.

# 클라이언트는 이 주소를 Anthropic이라 믿고 요청함
export ANTHROPIC_BASE_URL=http://localhost:8082
  • 설계 이유 — Bedrock·Vertex·사내 gateway 지원을 위해 벤더가 열어 둔 자리. 제3자 proxy도 같은 자리에 끼어듦
  • 대가 — 인증·감사 책임이 proxy로 이동

다른 곳에도 적용됨. 주소를 설정으로 뺀 프로토콜은 전부 중간자를 허용함.

2. 원리

proxy가 하는 일은 결국 스키마 번역 하나

// Anthropic (client → proxy)
{ "system": "be short",
  "messages": [{ "role": "user", "content": "hi" }] }
// OpenAI (proxy → upstream)
{ "messages": [{ "role": "system", "content": "be short" },
                { "role": "user", "content": "hi" }] }
  • content — 블록 배열 [{type,text}] → 문자열
  • 응답 — content[].text ↔ choices[0].message.content

3. 구조 이해하기

요청 한 번이 지나는 네 지점

실습 구성은 세 프로세스. 가짜 upstream 덕분에 API key 없이 왕복 관찰 가능.

4. 핸즈온

번역이 도는지부터 확인

docker compose up -d 후 Anthropic 포맷으로 요청

curl -s -X POST localhost:8082/v1/messages \
  -d '{"model":"claude-haiku-4-5","messages":[{"role":"user","content":"hi"}]}'

기대 결과

{"type":"message","model":"claude-haiku-4-5",
 "content":[{"type":"text","text":"[mock-small] you said: hi"}]}

체크포인트. Anthropic 껍데기 안에 OpenAI 백엔드의 답 — 번역 동작 확인.

4. 핸즈온

라우팅 결정을 눈으로 보기

모델 이름만 바꿔 두 번 호출. 셸 환경변수는 명시적으로 덮어씀

B=http://localhost:8082; C="python3 client/client.py hi"
ANTHROPIC_BASE_URL=$B $C
ANTHROPIC_BASE_URL=$B ANTHROPIC_MODEL=claude-sonnet-5 $C
# docker compose logs proxy
[proxy] claude-haiku-4-5 -> mock-small
[proxy] claude-sonnet-5  -> mock-big

체크포인트. 답한 모델은 proxy가 결정 — 비용 라우팅의 최소 형태.

4. 핸즈온

한계도 직접 만나기

실제 클라이언트가 항상 켜는 streaming을 요청

curl -s -X POST localhost:8082/v1/messages \
  -d '{"model":"claude-haiku-4-5","stream":true,"messages":[]}'

HTTP 400  {"error":"stream=true is not supported"}
  • 실제 proxy가 더 해야 하는 일 — SSE 이벤트 재구성, tool_use ↔ tool_calls 변환

체크포인트. 번역기 뼈대는 100줄, 쓸 만한 proxy의 대부분은 streaming과 tool 변환에 들어감.

5. 확인해 보기

스스로 점검

Q1. proxy 로그에는 요청이 안 보이는데 클라이언트는 401. 먼저 볼 곳은?

  • upstream API key 만료 여부
  • 클라이언트가 실제로 나간 주소 — 셸의 ANTHROPIC_BASE_URL
  • proxy의 모델 라우팅 규칙

로그에 요청 자체가 없으면 트래픽이 proxy에 오지 않은 것. 목적지를 정하는 건 환경변수.

5. 확인해 보기

스스로 점검

Q2. proxy를 붙인 뒤 에러 없이 느려지고 비용이 올랐다면?

  • 작은 모델로 라우팅됨
  • 클라이언트가 요청을 두 번 보냄
  • 번역 과정에서 prompt caching breakpoint 소실

번역 손실은 에러가 아니라 성능·비용 증상으로 나타남. 캐시가 깨지면 매번 전체 프롬프트를 재계산함.

6. 어디에 쓰이나

개인은 모델 교체, 조직은 통제 지점

  • 공급자 교체 — Anthropic 포맷을 OpenAI·Bedrock·Vertex·Ollama로 번역
    • ccproxy, claude-code-router, claude-code-proxy 계열의 주 용도
  • 비용 라우팅 — 짧고 쉬운 요청은 싼 모델, 어려운 요청만 큰 모델
  • 거버넌스 — 팀별 virtual key, rate limit, 예산, 감사 로그
  • 폐쇄망 — 외부 호출 출구를 한 곳으로 모음
  • 관측 — 여러 클라이언트의 지연·토큰·실패를 한 곳에서 수집

앞 두 개가 ccproxy 계열의 자리. 뒤 세 개는 AI gateway(LiteLLM, Bifrost)의 영역.

7. 트레이드오프

무엇을 얻고 무엇을 잃는가

얻는 것

  • 클라이언트 수정 없이 백엔드 교체
  • 모델 라우팅으로 비용 통제
  • 키·한도·감사를 한 지점에 모음
  • 폐쇄망 출구 단일화

잃는 것

  • 프롬프트 전문이 proxy를 통과 — 유출면 증가
  • 번역 손실이 조용히 발생
  • 단일 장애점 + 운영 부담
  • 클라이언트 업데이트마다 호환성 재검증

언제 쓰는가. 백엔드 교체·비용 통제가 목적이면 유효. 개인 실험이면 자체 proxy로 충분, 팀 운영이면 gateway 제품 사용이 안전.

8. 주의사항

공짜로 보이는 자리에 붙는 비용

  • 신뢰 — 프롬프트·소스코드 전문이 평문으로 통과
    • 남의 proxy 실행 = 코드 열람 허용. 디버그용 전문 로깅은 유출 저장소가 됨
  • 키 — 상위 공급자 키를 proxy가 보관. 회수·교체 책임이 이쪽으로 옴
  • 약관 — 구독을 API 모양으로 중계하면 계정 정지 위험. 팀에는 공급자 키나 Bedrock/Vertex
  • 번역 손실 — streaming·tool·caching·토큰 집계가 어긋나도 에러가 아님
    • "모델이 멍청해짐", "왜인지 느려짐"으로 나타나 디버깅이 오래 걸림
  • 운영 — 단일 장애점. 클라이언트 버전이 올라가면 새 필드에서 깨짐

9. 결론

도입 문제로 돌아가서

클라이언트는 Anthropic API만 알고, 백엔드는 OpenAI 호환이었음. 클라이언트가 목적지를 환경변수로 노출한 덕에, 그 자리에 스키마 번역기를 세워 코드 수정 없이 연결함. 모델 라우팅도 같은 지점에서 한 줄로 붙음.

기억할 원리 — "주소를 설정으로 뺀 프로토콜은 중간자를 허용한다". 그 중간자는 편의와 함께 프롬프트 전문과 키를 떠안으므로, 편의를 얻은 만큼 신뢰·번역 손실·운영 비용을 계산해야 함. 사람이 둘 이상 붙는 순간부터는 직접 만든 proxy 대신 gateway 제품이 다음 단계.
