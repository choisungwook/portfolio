# 평가가 에이전트 코딩의 루프를 닫아요

코드가 만들어졌다는 사실은 완료 조건이 아니에요.

Google Codelab은 식당 예약 에이전트를 심판하고, 실패 이유로 지침을 고친 뒤, 별도의 시험으로 다시 검증해요. 이 구조를 코딩에 옮기면 대상만 달라져요. 식당 예약은 코드 변경이 되고, 배고픈 손님은 실패한 테스트가 되며, 출시 게이트는 CI가 돼요.

이 글에서는 원문의 제품과 명령어보다 `응시자 → 심판 → 코치 → 게이트` 구조를 가져와요.

## 원문에서 가져올 것은 역할 분리예요

원문은 같은 모델에게 답변, 평가, 개선을 모두 맡기지 않아요. 각 역할이 만든 아티팩트도 분리해요.

| 원문의 역할 | 에이전트 코딩에서의 역할 | 아티팩트 |
| --- | --- | --- |
| 예약 에이전트 | Codex | 코드 diff |
| 결정론적 심판 | 테스트·정적 분석·정책 검사 | 점수와 실패 이유 |
| 지침 재작성 코치 | 실패 근거를 받은 다음 Codex 실행 | 다음 코드 diff |
| holdout 시험 | 코치에게 공개하지 않은 CI | 출시 판정 |
| 프로덕션 실패 수확 | 장애·리뷰·회귀 버그 | 다음 train 사례 |

왜 굳이 나눌까요? 코드를 만든 에이전트가 자기 결과를 말로 평가하면, 구현보다 설명을 잘하는 쪽으로 점수가 움직일 수 있거든요. 실행 가능한 테스트는 산문이 아니라 동작을 확인해요.

## 심판은 정답 문자열보다 동작을 봐요

코딩에는 같은 요구사항을 만족하는 구현이 여러 개 있어요. 모범 코드와 문자열이 비슷한지 재면 다른 정답을 실패로 만들어요. 함수 입력과 출력, API 계약, 성능 한도, 보안 정책처럼 관찰 가능한 결과를 확인하는 편이 맞아요.

이 실습의 심판은 경로 검증 함수에 8개 입력을 넣어요. 각 결과가 계약과 같은지만 확인하고, 구현 모양은 보지 않아요. Codex가 정규식을 쓰든 경로 조각을 순회하든 통과 조건은 같아요.

## 점수와 실패 이유는 하는 일이 달라요

점수는 게이트가 멈출지 결정해요. 실패 이유는 코치가 다음 변경을 만들 재료예요.

두 신호를 섞으면 문제가 생겨요. 코치가 holdout의 실패 이유까지 읽으면 시험을 학습 데이터로 바꿔 버려요. 반대로 점수만 주면 무엇을 고쳐야 하는지 알 수 없어요. 그래서 train은 실패 이유를 공개하고, holdout은 통과 여부만 공개해요.

OpenAI의 grader 설계 지침도 점수가 개선 정도를 보여야 하고, 평가의 허점을 이용하는 reward hacking을 막아야 한다고 설명해요. 코딩에서는 테스트 삭제, assertion 약화, 예외를 무조건 삼키는 변경이 대표적인 지름길이에요. 이 핸즈온은 심판 파일의 해시를 고정해 그런 변경이 생기면 루프를 멈춰요.

## 루프에는 반드시 벨트가 필요해요

뒤로 향하는 화살표 하나만 추가하면 반복은 만들 수 있어요. 하지만 종료 조건이 없으면 실패한 에이전트가 비용과 시간을 계속 사용해요.

여기서는 네 가지 벨트를 둬요.

- train을 모두 통과하면 holdout으로 이동해요.
- holdout을 모두 통과하면 `SHIP`으로 끝나요.
- 보호 파일이 바뀌면 즉시 중단해요.
- 최대 3회가 지나면 점수가 오르더라도 중단해요.

멈춘다는 것도 판정이에요. 자동화가 해결하지 못한 작업은 사람이 계약과 사례를 다시 살펴볼 차례예요.

## OpenAI에서는 로컬 게이트를 중심에 둬요

OpenAI 공식 문서의 `codex exec`는 Codex를 스크립트와 CI에서 비대화형으로 실행하는 인터페이스예요. 새 자동화에는 필요한 권한만 주는 `--sandbox workspace-write` 사용을 안내해요. 이 실습도 이 경계를 그대로 사용해요.

2026년 8월 기준 OpenAI Evals 플랫폼과 dataset 기반 prompt optimizer는 종료 일정이 공지된 전환 기능이에요. Evals는 2026년 10월 31일 읽기 전용, 11월 30일 종료 예정이에요. 그래서 새 코딩 루프의 핵심 게이트를 이 서비스에 묶지 않고, 저장소의 테스트와 Codex CLI로 재현해요. OpenAI의 grader 원칙은 가져오되 실행 책임은 CI가 가져가는 구성이에요.

에이전트 코딩의 핵심은 더 긴 프롬프트가 아니에요. 독립된 심판이 실패를 증거로 만들고, 다음 변경이 그 증거를 줄였는지 확인하는 구조예요.
