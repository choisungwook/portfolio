에디터는 어떻게 모르는 agent를 그리는가 — ACP

Agent Client Protocol의 전송·스트리밍·권한 구조를 직접 만들어 관찰

이런 상황이 있다면 — 에디터에서 Claude Code도 쓰고 Gemini CLI도 쓰는데 계획·diff·권한 창이 둘 다 같은 모양으로 뜸. 에디터가 두 agent를 각각 알고 만들었을 리는 없음.

어떻게 된 걸까?

1. 문제 상황

에디터 × agent = 통합 개수

Zed
JetBrains
Neovim
✕ 전부 연결
Claude Code
Gemini CLI
Codex

에디터 3 × agent 3 = 통합 9개. 하나 늘 때마다 곱셈으로 늘어남

  • agent를 하나 붙일 때마다 에디터마다 따로 만들어야 함
  • 결과적으로 사용자가 에디터에 갇힘. agent를 바꾸려면 에디터를 바꿔야 함

푸는 방법 중 하나 — 이미 같은 문제를 푼 선례를 반복.

2. 원리

LSP가 한 일을 agent에 다시 함

에디터와 언어 서버 사이에 규약 하나를 두어 N×M을 N+M으로 만든 것이 LSP. ACP는 같은 자리에 에디터와 코딩 agent를 넣음.

에디터 N
→
ACP규약 하나
→
agent M

사용자에게 더 중요한 두 번째 효과가 있음. ACP는 텍스트만이 아니라 계획·diff·권한 요청·터미널까지 규격화함. 그래서 에디터는 처음 보는 agent도 자기 UI로 그림. agent가 채팅창에 갇히지 않는 이유.

2. 원리

헷갈리는 지점 — 누가 client인가

MCP를 먼저 배운 사람이 가장 많이 뒤집어 이해하는 부분.

agentclient
→
파일·GitHub 서버server

MCP — agent가 client. agent가 도구를 불러 씀.

에디터client
→
agentserver

ACP — 에디터가 client. 에디터가 agent를 subprocess로 띄워서 부림.

에디터
ACP →
agent
MCP →
도구

코딩 agent는 ACP의 agent이면서 MCP의 client. 둘은 경쟁이 아니라 붙어 있음.

2. 원리

그래서 ACP는 MCP를 베껴 씀

ACP는 MCP의 ContentBlock 모양을 그대로 가져다 씀. agent가 MCP 도구의 출력을 변환 없이 에디터로 흘려보내기 위함.

여기에 MCP에 없는 세 가지를 더한 것이 ACP의 몫임.

  • diff — 고치기 전에 무엇이 바뀔지 보여줌
  • plan — 무엇을 할 계획인지 목록으로 보여줌
  • terminal — 실행 중인 명령의 출력을 붙여 보여줌

에디터 UX에 필요한데 MCP에는 없던 것들. 규약이 여기까지 정했기 때문에 에디터가 남의 agent를 자기 모양으로 그릴 수 있음.

3. 전송

선 위에는 무엇이 흐르는가

  • JSON-RPC 2.0. 새로 발명한 것 없음
  • 전송은 stdio. 에디터가 agent를 subprocess로 띄우고 stdin·stdout으로 말함
  • 메시지 하나가 곧 한 줄. 메시지 안에 개행을 넣지 못함
  • 파일 경로는 전부 절대경로, 줄 번호는 1부터

직접 만든 agent가 가장 흔하게 깨지는 방식 — stdout 오염

print("debug")            # ✕ stdout → 프로토콜 스트림이 깨짐
print("debug", file=sys.stderr)  # ○ 로그는 전부 stderr로

3. 전송

확인 문제

ACP에서 에디터와 agent의 역할로 맞는 것은?

  • 에디터가 client, agent가 server. 에디터가 agent를 subprocess로 띄움
  • agent가 client, 에디터가 server. MCP와 같은 방향
  • 둘 다 대등한 peer라서 아무나 먼저 연결을 엶
  • 중앙 브로커 서버가 있고 둘 다 거기에 붙음

MCP는 agent가 client이지만 ACP는 방향이 반대. 다만 요청은 양방향으로 오가서 agent도 에디터에게 요청을 보냄.

3. 전송

확인 문제

agent 코드에 print("done")을 넣으면 어떻게 되는가?

  • 에디터 채팅창에 done이 출력됨
  • stdout에 섞여 들어가 프로토콜 스트림이 깨짐
  • 무시됨. ACP가 알 수 없는 줄을 걸러 줌
  • 다음 session/update에 붙어서 전달됨

stdout은 프로토콜 전용. JSON이 아닌 줄이 들어가면 상대가 파싱에 실패함. 라이브러리가 배너를 찍는 것도 같은 사고를 냄.

4. handshake

없다고 쓰지 않으면 없는 것

client가 보내는 initialize — 이 실습의 실제 첫 줄

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
  "protocolVersion":1,
  "clientCapabilities":{"fs":{"readTextFile":true,"writeTextFile":true}}}}

protocolVersion은 정수 하나이고 현재 안정 버전은 1. 버전 숫자보다 중요한 규칙은 적지 않은 capability는 미지원이라는 것.

그래서 capability 추가는 절대 breaking change가 아니고, agent는 짐작하지 말고 받은 것을 확인해야 함.

5. 스트리밍

스트리밍은 채널이 아니라 notification

SSE도 WebSocket도 없음. 아직 답하지 않은 session/prompt를 붙들고 있는 동안 같은 파이프로 session/update를 계속 보냄.

client
prompt id:3 →
← update × N
← id:3 stopReason
agent
  • 요청에는 id가 있고 같은 id로 응답이 하나 옴. notification에는 id도 응답도 없음
  • id는 보낸 쪽 기준이라 client의 id 1과 agent의 id 1은 안 부딪힘

5. 스트리밍

무엇을 그릴지는 discriminator가 정함

최종 답변 한 조각 — 토큰이 흘러오는 모양

{"method":"session/update","params":{
  "sessionId":"sess_7d0b9ec",
  "update":{"sessionUpdate":"agent_message_chunk",
            "messageId":"msg_final",
            "content":{"type":"text","text":"Done. "}}}}

sessionUpdate 값이 무엇을 그릴지 알려줌. v1에 11종. messageId가 같으면 같은 메시지가 자라는 중.

턴이 끝나는 이유는 다섯 가지: end_turn, max_tokens, max_turn_requests, refusal, cancelled.

6. 권한

agent는 파일을 직접 열지 않음

agent경로는 앎
fs/read_text_file →
client
→
디스크

agent가 경로를 알면서도 스스로 open하지 않고 client에게 요청함. 실제로 파일을 여는 것도, 경로가 세션 디렉터리를 벗어나는지 검사하는 것도 client.

주의 — 이렇게 만들었다고 agent의 파일 접근이 사라지지는 않음. agent는 실행한 사람의 권한을 가진 프로세스라서, 협조할 때만 이 경로로 다님.

6. 권한

권한 창은 보안 경계가 아님

쓰기 전에 agent가 session/request_permission을 보내고 client가 답함. 거부되면 tool_call은 failed가 되지만 턴은 end_turn으로 정상 종료됨.

규약이 보장하는 것

  • 물었을 때 client가 판단할 자리
  • diff를 미리 보여줄 형식
  • 거부를 표현할 정상 경로

보장하지 않는 것

  • agent가 반드시 묻게 강제하지 못함
  • 안 묻고 그냥 하는 agent를 못 막음
  • 디렉터리 목록은 sandbox가 아님

스펙도 이를 인정하고 client가 OS 수준 sandbox를 따로 걸 것을 권고함.

7. 실습

한 턴을 흘려보고 선을 들여다봄

모델을 부르지 않는 agent라 매 실행이 같은 줄을 냄. 관찰에 적합함.

1단계 — 렌더된 결과, 2단계 — 원본 줄. 여기서부터가 본론

uv run python src/client.py "summarize the readme"

ACP_TRACE=1 uv run python src/client.py "summarize the readme" \
  2>&1 >/dev/null | grep '^\[client'

trace를 위에서 아래로 읽으며 확인할 것 — session/prompt(id 3)가 먼저 나가고 맨 마지막에 답이 옴. 그 사이 모든 update가 흐름.

7. 실습

권한과 capability를 각각 꺼 봄

uv run python src/client.py "..." --deny    # 쓰기 거부
uv run python src/client.py "..." --no-fs   # capability 미제공
  • --deny — tool_call이 failed가 되고 파일이 안 생김. 그런데도 stopReason은 end_turn
  • --no-fs — tool_call이 한 번도 나오지 않음. 호출이 막힌 게 아니라 그 세션에 도구가 애초에 없었음

"적지 않은 capability는 미지원"이 코드로 어떻게 나타나는지 보는 자리.

7. 실습

일부러 깨뜨려 보기

agent.py의 prompt() 맨 위에 넣고 실행

print("hello")

client가 파싱에서 실패함. 이 줄이 stdout으로 나가 JSON이 아닌 ACP 메시지가 되었기 때문.

log()로 바꾸면 회복됨. 손으로 만든 agent가 깨지는 가장 흔한 방식이라 한 번은 직접 깨뜨려 보는 편이 기억에 남음.

확인이 끝나면 test_acp.py로 허용·거부·capability 미제공 세 경로를 한 번에 검사할 수 있음.

주의 — SDK 버전과 프로토콜 버전은 무관. Rust crate는 2.x인데 Python은 0.x이고 둘 다 프로토콜 v1을 구현함.

9. 주의사항

보안과 전송에서 조심할 것

  • 권한 요청은 강제가 아님. 안 묻는 agent를 규약이 막지 못함. 막는 것은 client와 OS sandbox의 몫
  • 경로 검사는 client가 제대로 해야 함. 스펙도 심볼릭 링크를 고려하고 애매하면 실패시키라고 못박음
  • stdio가 유일한 안정 전송. HTTP는 draft, 원격 agent는 진행 중. 다른 머신의 agent는 아직 비포장도로
  • 채널 자체의 인증이 없음. authenticate는 agent별 문자열에 위임할 뿐 자격증명 전송 방식을 정의하지 않음

9. 주의사항

운영에서 걸리는 것

  • 취소 규칙이 까다로움. cancel 이후에도 update를 보낼 수 있지만 응답 전에 비워야 하고, 에러가 아니라 stopReason: cancelled로 끝내야 함
  • 터미널은 release해야 함. 내장 timeout이 없어 create·타이머·kill·output·release를 직접 조합
  • session/load는 비쌈. 전체 히스토리를 update로 다시 흘린 뒤 응답함
  • 스펙이 움직이는 중. v1은 안정이지만 v2 draft가 공개됐고 바뀔 것이라고 명시. npm 패키지 이름도 한 번 바뀜

9. 주의사항

확인 문제

client가 clientCapabilities에 fs를 넣지 않고 세션을 열었음. 무슨 일이 일어나는가?

  • agent가 fs/read_text_file을 부르고 client가 에러로 거부함
  • agent가 fs 도구를 아예 쓰지 않음. tool_call 자체가 나오지 않음
  • 기본값이 true라서 그냥 읽힘
  • initialize 단계에서 연결이 끊어짐

적지 않은 capability는 미지원. 호출을 막는 것이 아니라 그 세션에 도구가 존재하지 않는 것. --no-fs로 직접 확인할 수 있음.

9. 주의사항

확인 문제

사용자가 쓰기 권한을 거부했을 때 session/prompt의 결과는?

  • 정상 응답. stopReason은 end_turn
  • JSON-RPC 에러 -32603
  • stopReason: refusal
  • stopReason: cancelled

도구 거부는 정상 결과라서 턴은 end_turn으로 끝남. cancelled는 사용자가 턴 자체를 중단시켰을 때, refusal은 모델이 응답을 거절했을 때.

10. 결론

도입 질문으로 돌아가서

에디터가 두 agent를 각각 알고 만든 것이 아니라, 계획·diff·권한 요청의 모양만 규약으로 정해 두고 그 모양이 오면 자기 UI로 그린 것. agent가 무엇인지는 몰라도 됨.

그 대가로 파일 접근이 client를 거치게 되었고, 판단할 자리는 생겼지만 강제할 힘은 생기지 않았음.

기억할 원리 — 규약은 모양을 정할 뿐, 지키게 만들지는 못한다. 새 프로토콜을 볼 때 "이 규칙을 어기면 누가 막는가"부터 물으면 신뢰 경계가 어디인지 바로 보임.
