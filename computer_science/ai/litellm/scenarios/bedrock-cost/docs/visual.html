요청 하나가 두 장부에 적히는 과정

시나리오를 고르면 각 구간이 하는 일과 그 결과로 적히는 token이 바뀝니다.

LiteLLM 장부 (LiteLLM_SpendLogs)

Bedrock 장부 (CloudWatch, Cost Explorer)

input: LiteLLM은 세 종류를 더하고, Bedrock은 셋으로 나눕니다

LiteLLM prompt_tokens 53,156을 Bedrock의 기준으로 쪼갠 막대입니다. Cost Explorer의 input token 줄에 해당하는 것은 맨 왼쪽의 얇은 조각 하나입니다.

403 청구 대상 입력 (0.8%). Bedrock InputTokenCount 406에 대응, $3.00 42,008 Bedrock 캐시 읽기 (79.0%). 별도 지표, $0.30 10,502 Bedrock 캐시 쓰기 (19.8%). 별도 지표, $3.75 243 LiteLLM 응답 캐시 hit의 usage 재기록 (0.5%). Bedrock에는 없음

단가는 100만 token당입니다. LiteLLM은 prompt_tokens = inputTokens + cacheReadInputTokens + cacheWriteInputTokens로 적지만 비용은 세 값에 각각의 단가를 곱합니다. 그래서 금액은 맞고 token 수만 큽니다. 실패한 요청이 있으면 LiteLLM이 추정한 prompt_tokens가 다섯 번째 조각으로 붙습니다.

output: 방향이 두 가지입니다

output은 LiteLLM이 많을 때도, 적을 때도 있습니다. 원인이 서로 다릅니다.

응답 캐시 hit: LiteLLM이 많습니다

같은 요청 10건 중 9건은 Redis가 저장된 응답을 usage째로 돌려줍니다. LiteLLM은 10건 모두에 200을 적고 spend만 0으로 둡니다. Bedrock은 1건만 생성했습니다. 금액은 같습니다.

끊긴 스트림: Bedrock이 많습니다

client가 2초에 끊으면 LiteLLM은 그때까지 받은 chunk로 token을 추정합니다. Bedrock OutputTokenCount는 3건 모두 max_tokens 800까지 올라갔습니다. 금액이 어긋나는 유일한 경우입니다.

LiteLLM input이 40% 많다면 무엇이 섞인 것인가

LiteLLM prompt_tokens 중 Bedrock의 input 줄에 없는 token(캐시 읽기, 캐시 쓰기, 응답 캐시 재기록, 실패 추정)의 비중을 움직여 봅니다.

LiteLLM input이 Bedrock input보다 많게 보입니다.

비중 29%가 40% 차이에 해당합니다. 이 실험은 99.2%였습니다. 어느 조각이 그 29%인지는 scripts/report-input-gap.sh가 spend log에서 쪼개 줍니다.

두 장부를 비교할 때의 기준
