CLIENT → LITELLM → AI PROVIDER

web_search는
누가 실행하는가

tool call과 tool execution을 분리하고, 책임 경계를 직접 바꿔 봅니다.

오해: 모델에 tool을 주면 모델이 인터넷에 접속합니다.

완주: 같은 vLLM에서 client 소유와 LiteLLM 소유를 비교합니다.

먼저 예측

이 JSON 다음에 누가 움직여야 할까요?

{
  "name": "web_search",
  "arguments": "{\"query\":\"오늘 날짜 서울 날씨\"}"
}

이 출력은 검색 결과가 아닙니다. 모델이 만든 실행 요청입니다.

검색 서버에 실제 HTTP 요청을 보내는 주체는?

  • 항상 모델 프로세스
  • 설계가 지정한 client·gateway·provider runtime
  • OpenAI SDK가 자동 결정

tool call의 구조화와 tool의 실행은 서로 다른 책임입니다.

핵심 원리

한 번의 답변에는 최소 두 번의 모델 호출이 있습니다

① 질문
→
② tool call
→
③ 검색 실행
→
④ tool result
→
⑤ 최종 답변

[ 모델 호출: ①→②, ④→⑤ · 도구 호출: ②→③→④ ]

책임 위치를 바꿔도 이 상태 전이는 사라지지 않습니다.

시나리오 A

client가 loop를 소유하면 gateway는 트래픽만 봅니다

Clienttool loop + search HTTP
⇄
LiteLLMroute · auth · log
⇄
vLLMtool_calls 생성
  • 검색 query, timeout, 최대 round를 애플리케이션이 통제
  • LiteLLM 장애 범위에 search provider를 넣지 않음
  • client가 많으면 같은 loop가 반복됨

시나리오 A · 핸즈온

OpenAI SDK가 LiteLLM을 통과해 vLLM을 부릅니다

macOS Docker Desktop에서 CPU vLLM과 로컬 서비스를 올린 뒤 client-owned loop를 실행합니다.

docker compose --progress quiet up -d searxng
docker compose --progress quiet up -d vllm
docker compose --progress quiet up -d litellm
docker compose --profile client run --rm client-search

기대 결과

오늘 날짜와 서울 날씨 설명 ...
Sources: https://www.weather.go.kr/...

성공 판정. LiteLLM에는 두 model call이 보이고, 검색 HTTP 코드는 `client/app.py`에 있습니다.

시나리오 B

LiteLLM interception은 gateway를 agent runtime으로 바꿉니다

Client한 번만 호출
→
LiteLLMtool loop + SearXNG
⇄
vLLMtool_calls + answer

client는 최종 응답만 받습니다. 검색 key와 정책은 중앙화되지만, 검색 장애가 gateway 장애가 됩니다.

한 API call은 한 번의 upstream model call을 뜻하지 않습니다.

시나리오 B · 핸즈온

같은 vLLM, 다른 실행 주체

thin client는 `litellm_web_search`만 선언합니다.

docker compose --profile client run --rm gateway-search
docker compose logs --since=2m litellm

로그에서 찾을 흐름

vLLM → litellm_web_search(query)
LiteLLM → SearXNG
LiteLLM → vLLM(tool result)
LiteLLM → client(final answer)

성공 판정. client 코드에 SearXNG 호출이 없고 LiteLLM 로그에 interception이 있습니다.

시나리오 C

Nova Web Grounding은 Bedrock 안에서 검색을 끝냅니다

Client한 번만 호출
→
LiteLLM형식 변환 + routing
→
Nova 2 Lite검색 + 최종 답변

LiteLLM이 `web_search_options`를 `nova_grounding` system tool로 변환합니다. Bedrock이 검색과 재추론을 실행합니다.

응답에 grounding trace가 남아도 Client가 실행하거나 재호출할 대상은 아닙니다.

시나리오 C · 핸즈온

Client는 최종 답변과 citation만 사용합니다

로컬 AWS login session을 LiteLLM에 연결해 실행합니다.

make provider-bedrock

관찰할 흐름

Client → LiteLLM(web_search_options)
LiteLLM → Nova 2 Lite(nova_grounding)
Nova 2 Lite → Client(final answer + citations)

성공 판정. Client와 LiteLLM이 SearXNG를 호출하지 않고 최종 답변을 받습니다.

시나리오 D

vLLM Tool Server도 검색 loop를 소유할 수 있습니다

Client
→
LiteLLM
→
vLLM + Qwen
⇄
SearXNG MCP
  • vLLM Responses API와 `--tool-server`가 MCP browser를 실행
  • Qwen이 검색 결과를 받아 재추론하고 최종 답변 생성
  • LiteLLM은 interception 없이 인증과 routing만 담당
docker compose --profile client run --rm vllm-provider-search
docker compose logs --since=5m vllm searxng-mcp

Qwen2.5 non-Harmony MCP는 실험적이며 SearXNG upstream 상태가 답변 품질에 영향을 줍니다.

판단

LiteLLM은 트래픽만 관리해야 할까요?

기본값: 그렇습니다

  • route·auth·quota·logging에 집중
  • 서로 다른 client 정책을 강제하지 않음
  • 검색 장애의 blast radius 제한

예외: 중앙 실행

  • 많은 client가 같은 search key 사용
  • domain 정책을 한 곳에서 강제
  • 중복 loop보다 중앙 복잡도가 저렴

gateway 소유는 기능 추가가 아니라 책임 이전으로 결정합니다.

운영 체크

실행 위치보다 먼저 고정할 안전장치

  • 최대 tool round와 전체 deadline
  • 검색 query·domain allowlist와 egress policy
  • 검색 결과의 prompt injection 취급
  • 본문 인용 URL 보존과 사용자 출력 검증
  • model call과 search call의 공통 trace ID
  • 검색 결과 크기 제한과 민감 query logging 정책

어느 레이어든 이 목록을 소유하지 않으면, 책임은 분산된 것이 아니라 비어 있는 것입니다.

완주

두 로그를 비교하면 설계가 보입니다

  • Client 시나리오: tool 상태가 client 로그에 남음
  • LiteLLM 시나리오: interception과 두 upstream call이 gateway 로그에 남음
  • Bedrock 시나리오: Nova Grounding trace와 citation이 provider 응답에 남음
  • vLLM 시나리오: MCP search query가 serving runtime 로그에 남음

추천 시작점: client-owned loop + traffic-only LiteLLM.
