git이 비밀번호를 묻지 않는 이유 — credential helper

git HTTPS 인증의 위임 구조와 CodeBuild connection이 그 위에 올라타는 방법

이런 상황이 있다면 — CodeBuild가 토큰 없이 private repo를 clone하는데, buildspec 안에서 직접 실행한 두 번째 clone은 인증 실패로 죽음.

어떻게 풀까?

1. 문제 상황

첫 clone은 되는데 두 번째 clone은 실패

이런 상황을 가정함.

  • ✕ buildspec의 git clone https://github.com/... → fatal: Authentication failed
  • ✕ 반면 primary source는 토큰을 적은 적 없는데 정상 clone

PAT를 환경변수로 끼우는 임시방편은 로그 노출, 수동 갱신, 개인 계정 종속이 남음.

푸는 방법 중 하나 — git의 credential helper + buildspec의 git-credential-helper 옵션.

2. 원리

git은 자격증명 관리를 밖으로 밀어냄

  • 저장 방식은 환경마다 다름 — 키체인, 평문 파일, CI 토큰 발급
  • 내장하면 새 방식마다 git 수정 → 외부 프로그램과 텍스트로 대화만 정의

위가 질문(stdin), 아래가 답(stdout)

protocol=https
host=github.com
username=akbun
password=dummy-token

다른 곳에도 적용됨. docker-credential-*, kubectl exec plugin.

2. 원리

대화 규약 — get, store, erase

  • 이름 foo 지정 → PATH의 git-credential-foo 실행. ! 로 시작하면 셸 명령
  • 인자는 딱 하나 — get(요청), store(성공 통보), erase(401 통보)
  • 여러 개 가능. get은 순서대로 묻다 멈춤, store·erase는 전원에게 전달
  • 뒤에서 반드시 다시 만날 규칙 두 개
    • helper 빈 값 = 그때까지 쌓인 목록 리셋
    • useHttpPath = 구분 단위를 host에서 repo path로

HTTP(S) 한정. SSH는 ssh-agent 담당.

3. 구조 이해하기

git과 helper의 대화 한 사이클

구도 — git → helper → 자격증명 저장소. 뒤의 CodeBuild 그림도 같은 구도.

1
git push
→
credential helper
→
자격증명 저장소

1단계. git push가 인증 요구(401)를 받음. git은 비밀번호를 모름 — 알 필요 없게 설계됨.

2
git push
→
credential helperget
→
자격증명 저장소

2단계. helper를 get 인자로 실행, stdin으로 protocol·host 전달. useHttpPath가 켜져 있으면 path도.

3
git push
→
credential helper
→
자격증명 저장소키체인·파일·발급

3단계. helper가 자기 방식대로 찾음 — 키체인이든 신규 발급이든 git은 무관심.

4
git push성공
→
credential helperstore
→
자격증명 저장소

4단계. 성공하면 전 helper에 store, 실패하면 erase. 저장할지는 helper가 결정.

4. 핸즈온

프로토콜을 눈으로 보기

git credential fill — 묻는 과정을 직접 실행. 아래 # 뒤가 기대 결과

printf 'protocol=https\nhost=example.com\n\n' | git -c credential.helper='!printf "username=akbun\npassword=dummy-token\n" #' credential fill
# protocol=https
# host=example.com
# username=akbun
# password=dummy-token

체크포인트. 한 줄 셸 명령도 helper가 됨. 입력을 되돌려주고 자격증명 두 줄을 채워 줌.

4. 핸즈온

내장 helper로 저장까지

credential-store로 store → 파일 확인 → get. # 뒤가 기대 결과

printf 'protocol=https\nhost=example.com\nusername=akbun\npassword=dummy-token\n\n' | git credential-store --file ./creds store
cat ./creds        # https://akbun:dummy-token@example.com
printf 'protocol=https\nhost=example.com\n\n' | git credential-store --file ./creds get
                   # username=akbun
                   # password=dummy-token

체크포인트. 비밀번호가 평문으로 남음. CodeBuild는 이 자리에 무엇을 끼웠을까?

5. CodeBuild 원리

두 clone은 실행 주체가 다름

  • primary source — CodeBuild 서비스가 컨테이너 밖에서 connection 권한으로 받아 넣어 줌. 그래서 토큰 없이 성공
  • buildspec의 git clone — 컨테이너 안에서 새로 뜨는 평범한 git 프로세스. 자격증명 없음

connection = AWS CodeConnections 리소스. GitHub 조직에 AWS Connector for GitHub(GitHub App)를 설치하는 방식이라 장수 토큰을 저장하지 않고, 필요할 때 ghs_로 시작하는 installation access token을 발급. 1시간 뒤 만료.

남는 질문 — 컨테이너 안의 git에게 자격증명을 어떻게 공급할 것인가.

5. CodeBuild 원리

buildspec 한 줄이 helper를 심음

토큰을 환경변수로 심으면 수명(빌드 중 만료)과 노출(로그·자식 프로세스)이 문제. git에 이미 있는 "필요한 순간에 외부에 묻는" 자리를 차지함.

buildspec 스위치 → 컨테이너 git config. 4장의 규칙 두 개가 등장

env:
  git-credential-helper: yes
credential.usehttppath=true
credential.helper=
credential.helper=/codebuild/readonly/bin/git-credential-helper

5. CodeBuild 원리

helper는 토큰을 갖고 있지 않음

  • get이 올 때마다 컨테이너 안에 떠 있는 빌드 agent(localhost:7831)에 요청 전달
  • agent가 CodeBuild 서비스를 거쳐 connection에서 그 순간의 단명 토큰을 발급받아 응답
  • 쓰이는 권한 — service role의 codeconnections:GetConnectionToken

토큰이 파일로 상주하지 않아 노출면이 줄고, 매번 발급이라 만료 걱정 없음. git 입장에선 키체인이든 agent든 똑같은 helper.

helper 경로와 agent 포트는 공식 문서가 아닌 공개 역공학 분석 관찰값. 내부 구현은 변경 가능.

6. 반전

helper를 켜도 두 번째 clone은 여전히 실패

git-credential-helper: yes만 켜고 두 번째 repo를 clone한 결과

Error retrieving Git credentials.error code 400: GITHUB Git credential unavailable.
fatal: could not read Username for 'https://github.com/ORG/b.git'
  • 범인은 useHttpPath=true — 조회가 path 단위라 path=ORG/b.git으로 물음
  • agent는 source repo가 아닌 path에 자격증명을 내주지 않음
  • 단서는 실패 주체 — GitHub의 403/404가 아니라 agent의 400. GitHub까지 가지도 못함

7. 해법

source path로 토큰을 꺼내 재사용

발급 토큰은 repo 전용이 아닌 installation access token. 조회 경로만 맞추면 됨.

pre_build에서 한 번 실행 — 4장의 두 규칙이 쓰이는 지점

token=$(printf 'protocol=https\nhost=github.com\npath=ORG/a.git\n\n' | $HELPER get | sed -n 's/^password=//p')
printf 'https://x-access-token:%s@github.com\n' "$token" > "$CRED_FILE"
git config --global --replace-all credential.helper ""   # 목록 리셋
git config --global --add credential.helper "store --file=$CRED_FILE"
git config --global credential.useHttpPath false         # host 단위로 복귀

전역 config라 이후 스크립트는 평범한 git clone 그대로.

10. 확인해 보기

스스로 점검 ①

Q1. 빌드 로그에 error code 400: GITHUB Git credential unavailable 이 찍혔다. 가장 먼저 의심할 것은?

  • GitHub App installation에 그 repo가 빠져 있음
  • useHttpPath 때문에 source repo가 아닌 path로 조회됨
  • service role에 GetConnectionToken 권한이 없음

400을 낸 주체가 GitHub이 아니라 CodeBuild agent라는 것이 단서. 요청이 GitHub까지 가지도 못했으므로 installation 스코프 문제가 아님. installation 문제면 403/404로 나타남.

10. 확인해 보기

스스로 점검 ②

Q2. 해법에서 credential.helper에 빈 값을 넣고 useHttpPath를 false로 되돌리는 이유는?

  • CodeBuild helper가 store보다 느려서 성능을 위해
  • CodeBuild helper를 목록에서 비우고, 확보한 토큰이 host 단위로 매칭되게 하려고
  • 토큰을 평문 파일에 저장하려면 반드시 필요한 설정이라서

4장의 두 규칙 그대로. 빈 값을 넣지 않으면 CodeBuild helper가 먼저 조회되고, useHttpPath가 true면 store의 host 단위 항목이 path 조회와 매칭되지 않음.

11. 트레이드오프

무엇을 얻고 무엇을 잃는가

얻는 것

  • 토큰이 코드·환경변수에 남지 않고 자동 회전
  • 업무 스크립트는 평범한 git clone 유지
  • PAT의 개인 계정 종속에서 벗어남

잃는 것

  • helper만 켜서는 안 되고 path 우회가 필요
  • 토큰 권한이 조직 installation 전체 범위
  • helper 내부는 비공개 구현

언제 쓰는가. HTTPS로 private repo를 다루면 기본 선택지. 스코프를 좁혀야 하면 전용 GitHub App을 따로 두는 선택도 있음.

12. 결론

도입 문제로 돌아가서

두 clone의 실행 주체가 달랐음. primary는 CodeBuild 서비스가, 두 번째는 컨테이너 안 맨몸 git이 수행. git이 자격증명 관리를 외부 인터페이스로 밀어내 둔 덕분에 CodeBuild가 그 자리에 helper를 끼울 수 있었고, 같은 인터페이스의 규칙을 알아야 path 스코프 벽까지 넘을 수 있었음.

기억할 원리 — 비밀은 밖에 두고, 도구 안에는 인터페이스만 남긴다. 편의 옵션 하나로 끝나지 않을 때, 인터페이스의 규칙이 우회로가 됨.
