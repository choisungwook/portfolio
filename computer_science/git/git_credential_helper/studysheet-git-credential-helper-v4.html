git은 왜 비밀번호를 모르는가 — credential helper

git이 인증을 외부에 위임한 구조와, CodeBuild가 그 자리에 끼어든 방법

이런 상황이 있다면 — buildspec에 토큰을 적은 적이 없는데 git-credential-helper: yes 한 줄만으로 private repo가 clone됨.

어떻게 된 걸까?

1. 문제 상황

동작하는데 왜 되는지 설명할 수 없음

이런 상황을 가정함.

  • 토큰을 buildspec·환경변수 어디에도 넣지 않았는데 private repo clone 성공
  • ✕ 그런데 빌드 안에서 두 번째 private repo를 clone하면 인증 실패
  • ✕ 원인을 추측만 할 뿐, 토큰이 어디서 와서 어디에 있는지 설명 못 함

설명하지 못하면 보안 리스크도 판단할 수 없고, 다음에 비슷한 상황에서 응용할 수도 없음.

푸는 방법 중 하나 — git이 자격증명을 찾는 순서부터 확인하고, 그 순서의 한 자리인 helper를 관찰.

2. 원리

git이 자격증명을 찾는 순서

helper가 무엇인지보다 먼저 알아야 할 것. helper는 이 순서의 한 자리일 뿐임.

  • ① URL에 박혀 있으면 그것을 씀 — https://user:token@github.com/...
  • ② config의 credential.<url>.username 등 아는 항목을 채움
  • ③ credential.helper를 등록 순서대로 get 호출 — 다 차면 나머지는 건너뜀
  • ④ 못 채우면 사람에게 물음 — GIT_ASKPASS → core.askPass → SSH_ASKPASS → 터미널
  • ⑤ 결과 통보 — 성공이면 store, 401이면 erase를 등록된 모든 helper에 보냄

내 머신에서 clone이 비밀번호를 안 묻는다면, ①~④ 중 어디서 채워지는지가 첫 질문.

2. 원리

설정은 덮어쓰기가 아니라 누적됨

  • 읽는 순서 — /etc/gitconfig → ~/.gitconfig → .git/config → -c 옵션
    • GIT_CONFIG_SYSTEM·GIT_CONFIG_GLOBAL·GIT_CONFIG_NOSYSTEM으로 갈아끼울 수 있음
  • credential.helper만은 덮이지 않고 목록에 쌓임
    • 빈 값을 주면 그때까지 쌓인 목록이 리셋됨
  • 매칭 단위는 protocol + host 정확 일치. path는 보지 않음
    • credential.useHttpPath=true를 켜야 repo path까지 구분

이 두 규칙(빈 값 리셋, useHttpPath)이 뒤에서 CodeBuild 설정에 그대로 나타남.

2. 원리

helper는 무엇을 대신해 주는가

helper는 저장 장치가 아니라 git과 텍스트로 대화하는 외부 프로그램. 그 안을 git은 모름.

규약 전부 — 인자는 get·store·erase, 앞 두 줄은 git의 stdin, 뒤 두 줄은 helper의 stdout

protocol=https
host=github.com
username=x-access-token
password=ghs_...

다른 곳에도 적용됨. docker-credential-*, kubectl exec plugin이 같은 모양.

2. 원리

단명 토큰을 위해 규약이 늘어남

토큰이 짧게 살고 자주 바뀌는 시대가 오자, git은 본체를 고치는 대신 텍스트 규약에 필드를 늘림.

  • password_expiry_utc — 이 자격증명이 언제 만료되는지 git에게 알림
  • ephemeral — 저장하지 말라는 표시
  • oauth_refresh_token — refresh token을 함께 전달
  • authtype·credential — basic 외의 스킴(bearer 등)을 그대로 넘김
  • wwwauth[] — 서버가 보낸 WWW-Authenticate 헤더를 helper에게 전달

확장 지점을 텍스트 규약으로 잡아 둔 판단이 이 학습의 핵심. 새 인증 방식이 나와도 git은 그대로 둠.

4. 실습

토큰이 어디에 남는지 추적

빈 EC2에서 확인. 로컬은 기존 helper와 gitconfig가 관찰을 오염시킴. 실행 검증하지 않음.

URL에 토큰을 박고 clone한 뒤, 남은 자리를 찾음

git clone "https://x-access-token:$TOKEN@github.com/ORG/REPO.git" repo1
grep "url = " repo1/.git/config   # 토큰이 그대로 박혀 있음

git config --global credential.helper store
cat ~/.git-credentials              # store는 평문 파일로 옮겨 놓을 뿐

체크포인트. 리스크가 사라지지 않고 자리를 옮김. remote URL → 홈 디렉터리 파일.

4. 실습

디스크에 남기지 않는 helper 만들기

호출될 때마다 외부에서 토큰을 가져오는 helper를 직접 만들어 봄. CodeBuild helper와 같은 구조.

git-credential-ssm — PATH에 두면 credential.helper=ssm 으로 부를 수 있음

[ "$1" = "get" ] || exit 0
token=$(aws ssm get-parameter --name "$PARAM" --with-decryption --query Parameter.Value --output text)
echo "username=x-access-token"; echo "password=$token"

체크포인트. clone 후 .git/config와 ~/.git-credentials 어디에도 토큰이 없음. 대신 토큰을 얻을 권한이 파일 접근에서 IAM으로 이동함.

5. CodeBuild

두 clone은 실행 주체가 다름

  • primary source — CodeBuild 서비스가 컨테이너 밖에서 받아 넣어 줌. 그래서 토큰 없이 성공
  • buildspec의 git clone — 컨테이너 안에서 새로 뜨는 평범한 git. 자격증명 없음

connection은 AWS CodeConnections 리소스. 조직에 AWS Connector for GitHub(GitHub App)를 설치하는 방식이라 장수 토큰을 저장하지 않고 ghs_로 시작하는 installation access token을 발급. 1시간 뒤 만료.

남는 질문 — 컨테이너 안 git에게 자격증명을 어떻게 공급할 것인가.

5. CodeBuild

buildspec 한 줄이 심는 것

토큰을 환경변수로 심으면 수명과 노출이 문제. 3장 ③번 자리를 CodeBuild가 차지함.

스위치와, 그때 컨테이너 git config에 들어가는 설정. git은 출력에서 키를 소문자로 냄

env:
  git-credential-helper: yes
credential.usehttppath=true
credential.helper=
credential.helper=/codebuild/readonly/bin/git-credential-helper

4장의 두 규칙이 그대로 보임 — 빈 값으로 목록 리셋, useHttpPath로 조회 단위 전환.

5. CodeBuild

비공개 helper를 조회하는 방법

  • ① 설정 관찰 — git config --list --show-origin
  • ② helper 직접 호출 — 그냥 실행 파일이므로 git 없이 손으로 부를 수 있음
  • ③ 추적 — GIT_TRACE=1로 실행 순간을 봄. GIT_TRACE_CURL은 토큰이 찍히니 주의
  • ④ 정체 확인 — ls -la /codebuild/readonly/bin/, file, ps, ss -tlnp

② helper에 직접 물어보기. 토큰은 앞자리만 남기고 마스킹

printf 'protocol=https\nhost=github.com\npath=ORG/a.git\n\n' | /codebuild/readonly/bin/git-credential-helper get

6. 반전

helper를 켜도 두 번째 clone은 실패

12장 ②를 두 번째 repo path로 실행하거나, 그냥 clone했을 때

Error retrieving Git credentials.error code 400: GITHUB Git credential unavailable.
fatal: could not read Username for 'https://github.com/ORG/b.git'
  • 범인은 useHttpPath=true — 조회가 path 단위라 path=ORG/b.git으로 물음
  • 단서는 실패 주체 — GitHub의 403/404가 아니라 CodeBuild 쪽 400. GitHub까지 가지도 못함
  • 같은 helper인데 path만 바꾸면 결과가 갈림 = 권한 문제가 아니라 조회 스코프 문제

7. 해법

source path로 꺼내 재사용

발급 토큰은 repo 전용이 아닌 installation access token. 같은 installation의 다른 repo에도 유효.

pre_build에서 한 번 실행. H는 helper 경로, 4장의 두 규칙이 우회로가 됨

tok=$(printf '...\npath=ORG/a\n\n' | $H get | sed -n 's/^password=//p')
printf 'https://x-access-token:%s@github.com\n' "$tok" > "$CRED_FILE"
git config --global --replace-all credential.helper ""   # 목록 리셋
git config --global --add credential.helper "store --file=$CRED_FILE"
git config --global credential.useHttpPath false         # host 단위로 복귀

전역 config라 이후 스크립트는 평범한 git clone 그대로.

9. 트레이드오프

리스크는 사라지지 않고 이동함

얻는 것

  • 토큰이 config·파일·로그에 남지 않음
  • 호출 시점 발급이라 만료 관리 불필요
  • 업무 스크립트는 평범한 git clone 유지

잃는 것

  • 토큰 권한이 조직 installation 전체 범위
  • 발급 권한이 IAM으로 이동 — role을 쥔 쪽이 곧 토큰
  • helper 내부가 비공개라 관찰로만 파악

어디를 봐야 하나. "토큰이 어디 저장되나"가 아니라 "누가 토큰을 받아낼 수 있나". 파일 권한에서 IAM 권한으로 질문이 바뀜.

10. 확인해 보기

스스로 점검 ①

Q1. 빌드 로그에 error code 400: GITHUB Git credential unavailable 이 찍혔다. 먼저 의심할 것은?

  • GitHub App installation에 그 repo가 빠져 있음
  • useHttpPath 때문에 source repo가 아닌 path로 조회됨
  • service role에 토큰 발급 권한이 없음

400을 낸 주체가 GitHub이 아니라 CodeBuild 쪽이라는 것이 단서. 요청이 GitHub까지 가지도 못했으므로 installation 스코프 문제가 아님. 그 경우엔 403/404로 나타남.

10. 확인해 보기

스스로 점검 ②

Q2. 새로 만든 helper가 응답했는데도 git이 뒤 helper까지 계속 호출했다. 가장 그럴듯한 원인은?

  • helper가 종료 코드 0을 반환하지 않음
  • username만 출력하고 password를 출력하지 않음
  • helper 이름이 git-credential- 로 시작하지 않음

git은 username과 password가 모두 채워졌을 때 helper 호출을 멈춤. 일부만 주면 나머지를 채우러 다음 helper로 넘어감. 더 이상 묻지 않게 하려면 quit=true를 출력.

11. 결론

도입 질문으로 돌아가서

buildspec 한 줄이 한 일은 git 인증 순서의 ③번 자리에 자기 helper를 등록한 것. git은 비밀을 다루는 책임을 밖으로 밀어내고 텍스트 규약만 남겼기 때문에, AWS는 git을 고치지 않고도 그 자리에 들어올 수 있었음. 같은 규약의 세부 규칙(빈 값 리셋, useHttpPath)을 알아야 path 스코프 벽도 넘을 수 있었음.

기억할 원리 — 비밀은 밖에 두고, 도구 안에는 인터페이스만 남긴다. 다음에 비슷한 문제를 만나면 "이 도구에 위임 지점이 있는가, 없으면 어디에 만들 수 있는가"부터 물으면 됨.
