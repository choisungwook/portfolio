왜 파일 하나 보내는데 CPU가 바쁜가 — zero copy

같은 바이트를 네 번 복사하는 경로와, 그 중 두 번을 지우는 syscall

이런 상황이 있다면 — 네트워크도 디스크도 한가한데, 파일을 내려주는 서버의 CPU가 system time으로 꽉 참.

어디에 쓰이고 있는 걸까?

1. 문제 상황

계산은 안 하는데 CPU를 쓰는 프로세스

파일을 읽어서 소켓에 쓰기만 하는 서버를 가정함.

  • 애플리케이션 코드는 바이트를 들여다보지도 않음 — user time은 거의 0
  • ✕ 그런데 system time이 전송량에 비례해서 올라감
  • ✕ 스케일아웃으로 덮으면 비용은 늘고 원인은 그대로

커널 안에서 무슨 일이 일어나는지 모르면, 이 CPU가 줄일 수 있는 것인지 아닌지도 판단 못 함.

푸는 방법 중 하나 — 바이트가 실제로 몇 번 복사되는지 세어 보고, 그 중 없어도 되는 복사를 찾음.

2. 원리

read() + write()는 같은 바이트를 네 번 옮김

디스크
→
page cache커널
→
user buffer내 프로세스
→
socket buffer커널
→
NIC
  • ① 디스크 → page cache — DMA가 함. CPU는 쉼
  • ② page cache → user buffer — CPU가 복사. read()가 하는 일
  • ③ user buffer → socket buffer — CPU가 복사. write()가 하는 일
  • ④ socket buffer → NIC — DMA가 함. CPU는 쉼

①④는 데이터가 기계에 드나드는 비용이라 지울 수 없음. ②③은 바이트가 user space를 구경하러 갔다 온 값일 뿐임.

2. 원리

복사 말고 mode switch도 비용임

512MB를 64KB씩 보내면 read 8192번 + write 8192번 = syscall 16384번. 한 번마다 user mode와 kernel mode를 왕복함.

  • 복사 비용은 바이트 수에 비례함 — 메모리 대역폭을 먹음
  • mode switch 비용은 호출 횟수에 비례함 — 버퍼를 키우면 줄어듦
  • 둘은 다른 비용이라 따로 세야 함. 버퍼를 키워도 복사 횟수는 그대로 4번임

실습에서 BUFFER_SIZE를 64KB에서 4KB로 줄이면 syscall 수만 16배가 되고 복사량은 그대로임. 두 비용이 분리되는 지점.

3. 구조 이해하기

복사를 하나씩 지워 감

read + write — CPU 복사 2번, syscall 2번/청크. 기본 경로.

page cache
→
mmap 매핑복사 아님
→
socket buffer

mmap + write — page cache를 주소공간에 매핑만 하므로 ②가 사라짐. CPU 복사 1번.

page cache
→
socket buffer커널 안에서 끝
→
NIC

sendfile — user buffer라는 말 자체가 없음. fd 두 개를 커널에 넘기고 커널이 옮김. CPU 복사 1번, syscall 1번.

page cache
→
NICSG-DMA가 직접 읽음

sendfile + scatter-gather DMA — 커널은 page 위치만 socket buffer에 적어 두고, NIC이 page cache를 직접 읽어감. CPU 복사 0번. 이것이 "진짜 zero copy".

4. 코드

세 경로의 코드 차이

같은 파일을 같은 소켓으로 보내는 세 가지. 버퍼가 등장하는지만 보면 됨

// ① read + write — 바이트가 user space를 왕복
while ((n = read(file_fd, buf, 65536)) > 0)
    write(sock_fd, buf, n);

// ② mmap + write — 복사 대신 매핑
p = mmap(NULL, size, PROT_READ, MAP_SHARED, file_fd, 0);
write(sock_fd, p, size);

// ③ sendfile — 버퍼가 아예 없음
sendfile(sock_fd, file_fd, &offset, size);

③에 내 메모리 주소가 하나도 없다는 것이 핵심. 주소가 없으니 프로세스는 그 바이트를 볼 수 없고, 볼 수 없으니 복사할 이유도 없음.

5. 실습 결과

256MB를 세 경로로 보낸 값

서버가 스스로 센 값. syscall은 데이터를 옮기는 호출만 셈

mode=readwrite bytes=256.0MB wall=114ms user_cpu=4ms sys_cpu=110ms syscalls=8192
mode=mmap      bytes=256.0MB wall=77ms  user_cpu=0ms sys_cpu=75ms  syscalls=1
mode=sendfile  bytes=256.0MB wall=101ms user_cpu=0ms sys_cpu=86ms  syscalls=1
  • user_cpu가 0 — 계산은 정말 안 함. 그런데도 CPU를 씀
  • sys_cpu 차이가 지워진 복사 ②의 값
  • syscalls 8192 → 1 — 반복문이 user space에서 커널로 넘어감

wall time은 라운드마다 흔들림. loopback에서는 받는 쪽 nc가 같은 CPU를 나눠 쓰므로 wall은 두 프로세스의 합을 잼. sys_cpu와 syscalls를 봐야 함.

5. 실습 결과

이 수치는 보수적인 절반임

  • 실습은 loopback이라 NIC이 없음 → SG-DMA로 지워지는 마지막 복사는 관측되지 않음
  • mmap의 syscall이 1인 이유는 256MB를 write 한 번으로 넘겼기 때문. syscall 수와 복사 수는 다른 축
  • page cache를 미리 데워 두지 않으면 디스크를 재게 됨 — 준비 스크립트가 파일을 한 번 읽는 이유

측정 환경이 결과의 어느 부분을 못 보는지 먼저 적어 두면, 나중에 실제 장비에서 나온 숫자와 비교할 수 있음.

6. 한계

데이터를 만질 수 없음

sendfile이 빠른 이유가 바이트가 프로세스에 보이지 않기 때문이므로, 한계는 전부 이 한 문장에서 나옴.

  • 압축, 템플릿 치환, 체크섬, 요청별 본문 가공 ✕ — 전부 user space로 가져와야 함
  • 로그와 디버깅도 어려움 — 안 보이는 바이트는 로그에도 안 찍힘
  • 보통의 해법: 가공한 결과를 파일로 한 번 만들어 두고, 그 파일을 여러 번 sendfile

작은 파일에서는 아예 의미가 없음. 절약은 바이트 수에 비례하는데, 수 KB면 연결 수립과 왕복 지연이 훨씬 큼.

6. 한계

TLS를 켜면 이득이 사라짐

암호화는 바이트를 만지는 일임. 그래서 TLS 소켓에 그냥 sendfile 하는 길은 없음. HTTP에서 이득을 보던 정적 파일 서버가 HTTPS로 바꾸면 그 이득을 잃음.

  • kTLS — 암호화를 커널로 내려서 sendfile을 다시 쓸 수 있게 함
  • NIC TLS offload — 더 아래로 내림
  • 둘 다 설정과 드라이버 지원이 필요함 → 기본 가정은 "TLS면 복사 한 번 값을 낸다"

"무조건 sendfile을 켜라"가 아니라, 내 트래픽이 TLS인지 아닌지가 먼저라는 뜻.

7. 주변 도구

sendfile의 이웃들

  • splice — pipe를 경유해 임의의 fd 쌍을 이음. socket → socket 프록시에 씀
  • vmsplice — 내가 가진 page를 커널 pipe에 넘김
  • io_uring — 제출을 모아서 mode switch 자체를 줄임
  • MSG_ZEROCOPY — user buffer를 고정해 두고 send()에서 복사를 생략

sendfile은 가장 좁고 가장 이해하기 쉬운 도구(파일 → 소켓)임. 나머지는 그 단순함을 내주고 적용 범위를 넓힘.

8. 어디에 쓰이는가

이미 쓰고 있던 것들

  • Kafka — log segment를 page cache에서 consumer 소켓으로 sendfile. 브로커가 적은 CPU로 디스크 대역폭을 감당하는 이유의 큰 부분
  • nginx — 정적 파일 경로의 sendfile on
  • Netty FileRegion, Java FileChannel.transferTo — 같은 것의 언어 레벨 이름

공통점 하나. 앞단에 TLS를 세우거나 본문을 가공하는 필터를 끼우면 이 최적화는 조용히 사라짐. 사라져도 에러가 안 나므로 아무도 모름.

9. 트레이드오프

언제 고를 것인가

얻는 것

  • CPU 복사 감소 → 메모리 대역폭 여유
  • syscall 감소 → mode switch 감소
  • 같은 장비로 더 많은 연결 처리

잃는 것

  • 본문 가공·압축 불가
  • TLS와 충돌 (kTLS 없으면)
  • 전송 중 관측 수단이 반환값뿐
  • 작은 파일에서는 이득 없음

네트워크가 빨라지는 게 아님. 링크가 이미 포화면 이득은 처리량이 아니라 CPU 여유로 나타남.

10. 확인해 보기

스스로 점검 ①

Q1. read+write 서버에서 버퍼를 4KB에서 64KB로 키웠다. 무엇이 줄어드는가?

  • CPU가 하는 복사 횟수가 2번에서 1번으로 줄어든다
  • syscall 횟수가 줄어든다. 복사 횟수는 그대로 4번이다
  • DMA 전송량이 줄어든다

버퍼 크기는 호출 횟수를 바꿀 뿐 경로를 바꾸지 않음. 복사를 지우려면 경로 자체를 mmap이나 sendfile로 바꿔야 함.

10. 확인해 보기

스스로 점검 ②

Q2. 정적 파일 서버에 HTTPS를 붙였더니 같은 트래픽에서 CPU가 크게 올랐다. 먼저 의심할 것은?

  • page cache miss가 늘어 디스크를 더 읽는다
  • sendfile 경로가 빠지면서 암호화 복사가 user space로 돌아왔다
  • syscall 버퍼 크기가 작아졌다

암호화는 바이트를 만지는 일이라 sendfile과 같이 갈 수 없음. 확인할 것은 kTLS 사용 여부와, 그것이 없다면 이 CPU가 지금 구조에서는 정상 비용이라는 판단.

11. 결론

도입 질문으로 돌아가서

계산하지 않는 프로세스가 CPU를 쓰고 있었다면, 그 CPU는 대개 바이트를 user space로 데려왔다가 도로 내보내는 복사임. 프로세스가 그 바이트를 볼 이유가 없다면 커널 안에서 끝내면 되고, sendfile은 그 "볼 이유가 없다"를 syscall 모양으로 표현한 것임.

기억할 원리 — 데이터를 보지 않겠다고 선언하면 복사를 지울 수 있다. 반대로 보겠다고 하는 순간(압축, TLS, 가공) 값을 다시 내야 함. 그래서 이것은 성능 스위치가 아니라 내 서버가 데이터를 만지는가에 대한 설계 질문임.
